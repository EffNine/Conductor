# P3.15 Routing Trace Persistence — Report

Stage: P3.15 (persistence foundation for routing decision traces)
Base: P3.14 complete (canonical DecisionTrace contract, verified)
Date: 2026-08-19

---

## 1. Executive Summary

Every completed Conductor routing decision is now durable and queryable.
`DecisionPipeline` publishes the final `DecisionTrace` on the existing
`DecisionFinished` event; a new event-bus consumer (`TracePersistence`)
saves it asynchronously into SQLite via a new `TraceStore` implementation
(`SQLiteTraceStore`). The store retains the complete canonical trace payload
as JSON and exposes the queryable dimensions (mode, provider, model, runtime
hash, outcome, score, candidate count, timestamps) as indexed columns.

Persistence is fully decoupled from routing correctness:

- Persistence happens **after** the decision completes, through the event
  boundary — never inside a pipeline stage.
- Persistence is **asynchronous** — a save never blocks the request path.
- Persistence **failure is isolated** — save errors are logged and dropped;
  a broken store can never fail or alter a routing request.
- Persistence acquires **no second RuntimeSnapshot** — the trace (built from
  the decision's single snapshot) is the only payload.
- RouterEngine, DecisionPipeline, and the handler have **no SQL dependency**;
  SQLite ownership stays in `internal/database`.

Verified end-to-end with the real binary: a live request through the gateway
produced a `routing_traces` row with all queryable dimensions and a 2.3 KB
canonical payload containing no prompt content.

## 2. Existing Database Architecture

Audit findings (no persistence mechanism was duplicated):

- **Connection**: `internal/database/database.go` — GORM over
  `mattn/go-sqlite3`, WAL mode, `synchronous=NORMAL`, `busy_timeout=5000`,
  `MaxOpenConns` from config (default 10). This is the single SQLite owner.
- **Migrations**: GORM `AutoMigrate` driven by `Database.Migrate()`,
  registering every model struct. There is **no versioned migration
  framework**; the mechanism is additive `CREATE TABLE IF NOT EXISTS` +
  index creation. `routing_traces` joins this list.
- **Tables**: `usage_records`, `request_logs`, `provider_health_records`,
  `cost_rates`, `model_status_records`, `model_probe_meta` (database
  package) plus task tables via `task.MigrateTasks`. None is a generic
  event/audit table — `request_logs` is an HTTP-access log, not a routing
  record.
- **Transactions**: GORM `Create`/`Save` single-statement writes (e.g.
  `usage.Tracker`, health persistence). No multi-statement transaction
  patterns exist in the codebase; a single-row insert is atomic in SQLite
  and needs no wrapping transaction.
- **Concurrency**: WAL + busy_timeout; GORM pool of up to `MaxOpenConns`
  connections; SQLite serializes writers internally.
- **Retention/cleanup**: none exists anywhere (no TTL jobs, no pruning).
- **JSON conventions**: usage/log tables store flat columns, not JSON;
  payload-style JSON does not exist yet — `routing_traces.payload_json` is
  the first (and canonical) JSON column.
- **Write patterns**: parameterized GORM queries throughout; no string
  concatenation with user input.

Conclusion: reuse GORM + `AutoMigrate` + the existing `*gorm.DB`. No second
persistence mechanism was introduced.

## 3. Trace Persistence Contract

```
RuntimeSnapshot      = routing truth         (unchanged, P3.14)
DecisionTrace        = decision explanation  (unchanged, P3.14)
TraceStore           = historical persistence (NEW, P3.15)
Metrics/Telemetry    = operational evidence   (unchanged)
Provider execution   = independent of trace persistence
```

Persistence contract (all verified by tests):

1. A trace is persisted only **after** the routing decision completes.
2. The persisted artifact is the **final** canonical `DecisionTrace`
   (winner, candidate scores, rejection reasons, effective weights, mode
   metadata, runtime hash, stage results, timeline events).
3. Serialization uses the canonical P3.14 JSON contract: deterministic,
   secret-free, prompt-free, request-body-free.
4. Persistence never influences selection, never acquires a second snapshot,
   never fails the request.
5. Both successful **and failed** decisions persist.
6. Retrieval by decision ID returns the full canonical trace; listing
   returns queryable summaries without payload deserialization.

## 4. TraceStore Interface

`internal/router/trace_store.go` — internal, no HTTP exposure.

```go
var ErrTraceNotFound = errors.New("trace not found")

type TraceStore interface {
    Save(ctx context.Context, trace *DecisionTrace) error
    Get(ctx context.Context, decisionID DecisionID) (*DecisionTrace, error)
    List(ctx context.Context, filter TraceFilter) ([]DecisionTraceSummary, error)
}

type TraceFilter struct {
    Mode        string    // resolved_mode
    Provider    string    // selected_provider
    Model       string    // selected_model
    RuntimeHash string    // runtime_hash
    Outcome     string    // selected | rejected | failed
    From        time.Time // >= decision timestamp
    To          time.Time // <= decision timestamp
    Limit       int       // default 100, cap 1000
    Offset      int
}

type DecisionTraceSummary struct { /* the 14 queryable columns, see §5 */ }
```

Notes:

- The P3.14-era stub interface (`Save/Load/Latest/Search` with a
  provider/model/time filter set) had **no implementations and no callers**
  beyond the pipeline's unused `Save` hook; it was reshaped into the
  canonical P3.15 contract. `ErrTraceNotFound` is part of the interface
  contract so `Get` returns a clear, checkable not-found error.
- `Outcome` was added to the spec's suggested filter set because §13
  ("failed decisions") is an explicit future query; it is the only
  extension beyond the spec's list, and it is a single exact-match column,
  not a query language.
- The interface lives in `router` (next to `DecisionTrace`); the
  implementation lives in `database`. The storage layer knows nothing about
  Fiber, HTTP, provider execution, or routing selection logic.

## 5. SQLite Schema

Table `routing_traces` (registered in `Database.Migrate()`):

| column | type | purpose |
|---|---|---|
| `decision_id` | TEXT PK | canonical decision identity |
| `timestamp` | DATETIME | decision time (ordering + time-range filters) |
| `schema_version` | INTEGER | trace schema version (contract versioning) |
| `requested_mode` | TEXT | raw mode from request |
| `resolved_mode` | TEXT | canonical resolved mode |
| `mode_source` | TEXT | explicit \| classifier |
| `task_type` | TEXT | intent task type (chat/coding/…) |
| `selected_provider` | TEXT | winner provider (empty when rejected/failed) |
| `selected_model` | TEXT | winner user-facing model ID |
| `runtime_hash` | TEXT | exact runtime snapshot identity (64 hex) |
| `selected_score` | REAL | selected candidate TotalScore (0 if none) |
| `candidate_count` | INTEGER | number of scored candidates |
| `outcome` | TEXT | selected \| rejected \| failed |
| `payload_json` | TEXT | **canonical** DecisionTrace payload (source of truth) |
| `created_at` | DATETIME | insert-time audit |

Design decisions:

- **No nested-field duplication.** Candidate scores, rejection reasons,
  weights, bonuses, stages, and events live only in `payload_json`. The
  columns exist strictly for the query dimensions of §13.
- `payload_json` remains the **only** detailed trace representation — there
  is no second trace schema (§5 of the spec).
- `outcome` is derived at save time from the trace itself (see §11), so the
  `DecisionTrace` struct was not modified and no schema bump was needed.
- Saves are idempotent: re-saving an existing `decision_id` is a no-op
  (`ON CONFLICT DO NOTHING`) — safe against event replays.

## 6. Index Strategy

Five indexes, each justified by a realistic future query (§13):

| index | serves |
|---|---|
| `idx_routing_traces_timestamp` | "recent decisions", time-range scans |
| `idx_routing_traces_timestamp_mode` (ts, resolved_mode) | "decisions by mode", "mode over time" |
| `idx_routing_traces_timestamp_provider` (ts, selected_provider) | "decisions by provider", "provider over time" |
| `idx_routing_traces_selected_model` | "decisions by model" |
| `idx_routing_traces_runtime_hash` | runtime/decision correlation, regression lookups |

Deliberately **not** indexed: `outcome` (failure queries are always
time-windowed and the timestamp index covers the scan; add
`(timestamp, outcome)` only if failure-rate dashboards need it), `task_type`
(no planned query), `decision_id` (PK, implicitly indexed). SQLite uses one
index per query; the composite indexes carry the leading `timestamp` column
so pure-time queries are covered by `idx_routing_traces_timestamp`. Write
cost: 5 index updates per insert (~µs each, WAL).

## 7. Serialization Contract

Persisted payload = `encoding/json.Marshal(DecisionTrace)` with the P3.14
canonical struct tags — the same serialization P3.14 tested for safety.

1. Deterministic: Go's `encoding/json` sorts map keys; all trace fields are
   ordered struct fields. Same trace ⇒ same bytes (round-trip test compares
   marshaled bytes exactly).
2. No secrets: the trace contract has no key/header fields (§16 verifies
   the persisted bytes).
3. No prompts / raw request bodies: `DecisionContext.Request()` is never
   referenced by the builder or the store.
4. Candidate scores, rejection reasons, runtime hash, effective weights,
   mode bonuses, mode metadata, stage results, and events all survive
   byte-identical round trips.
5. **Pre-persist validation**: `Save` marshals before inserting; a marshal
   failure returns an error to the consumer (logged, request unaffected) —
   an unserializable trace can never poison the table.
6. No second trace representation exists: `Get` unmarshals `payload_json`
   back into the same `DecisionTrace` type (lossless by construction).

## 8. Save Lifecycle

```
DecisionPipeline.Execute()
  ↓  stage execution (unchanged)
  ↓  populateTraceFromContext (no snapshot, no provider calls)
  ↓  builder.Build() → final DecisionTrace
  ↓  publish DecisionFinished (payload = final trace)      ← sync, in-process
  ↓  publish DecisionTraceCreated (payload = final trace)  ← unchanged, P3.14
  ↓  [request continues to provider execution]
TracePersistence.handle (subscriber)
  ↓  acquires bounded slot, spawns goroutine
  ↓  SQLiteTraceStore.Save (background context + 5s timeout)
```

- Persistence starts only after the routing decision is complete; the save
  happens after `Execute` returns (asynchronously).
- Provider selection and provider execution never wait on or interact with
  the store.
- On the failure path (stage failure) `DecisionFinished` is now also
  published with the failure trace — the decision did finish, and §11
  requires failed decisions to persist. (P3.14 previously published only
  `DecisionTraceCreated` on failure; the failure trace content is
  unchanged.)

## 9. EventBus Integration

Audited existing events: `DecisionStarted`, `IntentResolved`,
`CapabilityResolved`, `CandidatesGenerated`, `ProviderSelected`,
`DecisionFinished`, `DecisionTraceCreated`.

- `DecisionFinished` previously carried the `DecisionContext` as payload and
  fired **before** the trace was built. Minimal extension: the trace is now
  built first and `DecisionFinished` carries the **final `DecisionTrace`**
  (§8 spec: "If DecisionFinished currently lacks the final trace, minimally
  extend it"). Existing subscribers (tests) do not inspect the payload.
- The persistence consumer subscribes **only** to `DecisionFinished` — the
  spec's preferred chain (`DecisionPipeline → final trace →
  DecisionFinished → persistence consumer`). No duplicate decision events
  were created; `DecisionTraceCreated` remains the P3.14 observability event
  with its payload contract unchanged.
- No other subsystem subscribes to `DecisionFinished`; the pipeline remains
  the sole publisher.

## 10. Sync/Async Decision

**Async, via the existing event bus.** Rationale:

- The architecture already has an event bus with bounded subscriber
  concurrency — the spec's preferred precondition (§7).
- A synchronous insert (~100 µs, §18) would sit on the critical path
  between decision completion and provider execution for **every** request;
  async persistence adds ~0 µs to provider-facing latency.
- No new queue infrastructure was introduced: the consumer uses a fixed
  semaphore (16 concurrent saves) plus one goroutine per trace — the same
  bounded-concurrency-with-drop pattern the bus itself uses.
- Under saturation, traces are dropped with a warning log (like the bus's
  own drop behavior). At ~100 µs/save this allows ~10k saves/sec of headroom
  before the limit matters; traces are observability, not correctness.
- Durability trade-off (documented): a process crash between decision and
  save can lose a trace. This is acceptable for an observability store and
  is the price of keeping persistence off the request path; `Stop()` drains
  in-flight saves on graceful shutdown.

## 11. Failure Semantics

Both successful and failed decisions persist (verified by
`TestFailedDecisionPersistsTrace`, `TestTraceOutcomeDerivation`):

- **selected** — winner present (normal routing outcome).
- **rejected** — decision completed with no selected candidate (all
  candidates hard-rejected: vision / context / planning / agentic /
  circuit-breaker / invalid-candidate).
- **failed** — a pipeline stage failed before selection (intent
  rejection, capability failure, no candidates, etc.).

`outcome` is **derived from the trace** at save time (failed stage present ⇒
`failed`; else winner ⇒ `selected`; else `rejected`), so the DecisionTrace
contract itself needed no modification and rejection reasons are preserved
verbatim in the payload (`RejectionReasons` + per-candidate
`RejectionReason`).

Sanitization: stage-error metadata (`map[string]any{"error": ...}`) contains
only routing-stage errors — provider execution errors never enter the
pipeline or the trace, so no provider responses or sensitive content can be
persisted through this path.

## 12. Trace Query Contract

`List` supports exactly the minimum filter set for future dashboard work:

- by mode, provider, model, runtime hash, outcome (exact matches)
- time range (inclusive, on decision `timestamp`)
- pagination (limit default 100, cap 1000; offset; deterministic order
  `timestamp DESC, decision_id DESC`)

All filters are parameterized GORM `WHERE` clauses — no SQL string
concatenation with user-controlled values. `Get(decisionID)` returns the
full trace or `ErrTraceNotFound`. No arbitrary query language.

## 13. Retention Considerations

No automatic retention was built (the database has no existing retention
mechanism; the spec forbids it this stage). Facts for the future:

- **Expected size**: one row per routing decision. Payload ≈ 1.9 KB
  (2-candidate trace, measured) scaling roughly with candidate count
  (~0.5–1 KB per candidate + fixed ~1 KB overhead).
- **Growth**: ≈ 2.1–2.5 KB/request on disk (payload + row + 5 index
  entries + WAL amortization). 1k requests ≈ 2.5 MB; 10k ≈ 25 MB;
  100k ≈ 250 MB. At 1 req/s this is ≈ 216 MB/month.
- **Index implications**: 5 indexes × ~100 bytes/row ≈ +0.5 KB/request
  overhead; the 5 indexes add up to ~15–25% of table size.
- **Future strategy** (not built): age-based pruning (`DELETE FROM
  routing_traces WHERE timestamp < ?`) in a periodic job, with
  `(timestamp)` index serving the scan; or tiered retention (keep
  summaries, drop payloads after N days) if disk is a concern. The schema
  supports both without changes.

## 14. Execution Outcome Boundary

Routing decision outcome ≠ provider execution outcome.

At the moment `DecisionFinished` fires, provider execution **has not
started** (execution follows selection in the handler), so no execution
outcome is available at trace-finalization time. Per the spec:

- P3.15 persists the **routing decision** only.
- Execution telemetry remains in `RuntimeSnapshot`/telemetry systems
  (P3.7/P3.10) — the TraceStore is **not** an execution log.
- Future correlation (e.g. "did the routed provider succeed?") belongs to a
  later stage, joining execution telemetry to `decision_id` — explicitly
  out of scope here.

The `outcome` column (§11) is the routing-decision outcome and must never be
read as execution success/failure.

## 15. Security / Sensitive Data Audit

- Trace construction (P3.14) never embeds prompts, API keys, authorization
  headers, provider credentials, or the raw request body; `Save` serializes
  only the trace.
- `TestTracePayloadDoesNotContainSecrets` asserts the persisted bytes
  contain no `sk-`, `api_key`, `authorization`, `bearer`, `x-api-key`,
  `secret`, or `password` strings.
- `TestTracePayloadDoesNotContainPrompt` asserts no message/role/content
  keys or prompt text persist.
- Verified live: the end-to-end smoke test's persisted payload (2.3 KB)
  contained the routing dimensions and no request content.
- Stage-error metadata holds only routing errors (no provider responses).
- `Get`/`List` are parameterized; `decision_id` is a UUID, not user input.
- No trace data is exposed via HTTP in this stage (no new endpoints).

## 16. Concurrency

- `SQLiteTraceStore` uses the shared GORM pool (WAL + busy_timeout);
  concurrent writers are serialized by SQLite with bounded wait; concurrent
  readers run in parallel. `Save` is a single atomic statement.
- `TracePersistence` bounds goroutines with a 16-slot semaphore; slot
  acquisition + `WaitGroup.Add` are serialized under a mutex so `Stop()`
  (unsubscribe → wait) can never miss an in-flight Add. The event's context
  is **never** used for the save (decision lifecycle cancels it) — saves
  use `context.Background()` + 5 s timeout.
- Verified with `TestConcurrentTraceWrites` (20 goroutines × 5 writes),
  `TestConcurrentTraceReadsAndWrites` (mixed readers/writers), and the full
  `-race` suite.

## 17. Migration

- `routing_traces` + its 5 indexes are created by the existing
  `AutoMigrate` mechanism — the same additive migration path every other

- Verified: fresh DB (`TestRoutingTraceMigration` creates the table; live

## 18. Performance

Benchmarks (AMD Ryzen 7 5700X, `-benchtime=1s`, count=3, on-disk WAL DB):

| benchmark | result |
|---|---|
| `BenchmarkTraceStoreSave` (unique ID, full trace) | **≈ 104 µs/op**, ~19.9 KB alloc, 148 allocs |
| `BenchmarkTraceStoreList` (mode filter, 50 of 1000 rows) | **≈ 45 µs/op**, ~15.3 KB alloc |
| `BenchmarkTracePayloadSize` | **≈ 1.9 KB** payload, ~12 µs marshal |

- Insert cost is dominated by the SQLite write + 5 index updates
  (approximately 2–3× the raw JSON marshal). The JSON marshal alone is
  ~12 µs; the store adds one marshal + one insert per save.
- Because persistence is async, **provider-facing latency increase ≈ 0**;
  the only request-path cost is building the trace (P3.14: ~2.3 µs) and a
  channel send + goroutine spawn (sub-µs).
- No premature optimization: current insert throughput (~10k/s) exceeds the
  gateway's realistic request rate by orders of magnitude.

## 20. Bugs Found

1. **P3.14-era `TraceStore` stub was dead code** — an interface with
   `Load/Latest/Search` no implementation or caller could satisfy; the
   pipeline's `saveTrace` hook was never wired anywhere in production.
2. **`DecisionFinished` fired before the trace existed** — the payload was
   the decision context and the final trace was built afterwards, making the
   spec's preferred event chain impossible without reordering.
3. **Failure decisions never published `DecisionFinished`** — they would
   have been invisible to a `DecisionFinished` persistence consumer.
4. (Test-only) naive secret-substring assertions in early drafts matched
   test IDs and the legitimate `MaxTokens` policy field — not product bugs,
   but they validated that absence checks must target credential-shaped
   strings, not generic vocabulary.

---

## 21. Bugs Fixed

1. Reshaped the stub into the canonical `TraceStore` contract
   (`Save/Get/List` + `TraceFilter` + `DecisionTraceSummary` +
   `ErrTraceNotFound`) and removed the never-wired pipeline `traceStore`
   field and `saveTrace` path (replaced by the event-driven consumer —
   persistence is now actually reachable in production).
2. Reordered trace finalization: the trace is built **before**
   `DecisionFinished` is published, and the event carries the final trace.
3. `DecisionFinished` is now published on the failure path with the failure
   trace, so failed decisions persist (§11).
4. Benchmarks initially measured the `ON CONFLICT DO NOTHING` no-op path
   (reused decision ID); switched to unique IDs so the benchmark measures
   true insert latency.

## 22. Intentional Behaviors

- **Async persistence with drop-on-saturation**: traces can be lost under
  extreme load or on crash; observability semantics, per spec.
- **Outcome derived at save time** (not stored on the trace): keeps the
  P3.14 `DecisionTrace` contract untouched; the trace remains the single
  source of truth and the store derives the column.
- **`outcome` filter added to `TraceFilter`** beyond the spec's literal
  list — required by the "failed decisions" future query (§13).
- **Time-range filters on `timestamp`** (decision time), not `created_at`
  (insert time): "recent decisions" means decision time.
- **`ON CONFLICT DO NOTHING` idempotent saves**: re-saving the same
  decision ID is a no-op, safe against event replays.
- **`DecisionFinished` payload change** (context → trace): existing
  subscribers don't inspect payloads; the spec's preferred chain requires
  the trace at that event.
- **Consumer gated on `routing.enabled`**: without the pipeline no
  `DecisionFinished` exists.

---

## 23. Architecture Debt

1. **No versioned migrations**: schema changes rely on GORM `AutoMigrate`
   additivity; a future column-rename/drop needs a real migration layer.
   (Pre-existing; unchanged.)
2. **No retention job**: `routing_traces` grows unboundedly until §13's
   strategy is implemented (≈ 2.5 MB per 1k requests).
3. **Payload can't be partially updated**: an `outcome` refinement (e.g.
   post-hoc execution linkage) would need either a new column or a payload
   rewrite; both are future work, not this stage.
4. **`DecisionTraceCompleted` event still unpublished** — reserved for the
   stage that surfaces persistence completion to dashboards.
5. **Index cost on write**: 5 indexes per insert is acceptable at current
   rates; if trace volume grows 100×, re-evaluate dropping the two
   composite indexes in favor of `(timestamp)` + single-columns.
