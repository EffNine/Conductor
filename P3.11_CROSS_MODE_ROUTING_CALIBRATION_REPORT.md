# P3.11 Cross-Mode Routing Calibration & Semantic Verification Report

Date: 2026-08-19
Scope: `internal/router` (selection, scorer, pipeline stages, mode profiles, context estimation, classifier) + `internal/handler` (cache key, fallback execution) + `internal/runtime` (telemetry/state snapshot).

## 1. Overview

This stage proved that Conductor's 8 public routing modes (`auto`, `coding`, `reasoning`, `vision`, `fast`, `planning`, `agentic`, `long_horizon`) each produce their intended decision behavior across runtime state, capability metadata, context budget, and execution telemetry. Work product: 3 correctness fixes, 1 dead-code cleanup, 51 new regression/calibration tests, and a full verification pass (`test`, `build`, `race`, `race -count=10`).

## 4. Weight Effectiveness Audit

- `Normalize` invariants: sums to 1.0, each weight in [0,1]; zero/negative raw weights fall back to equal weights (0.25 each), no NaN/panic (`TestP311NormalizeSumsToOne`, `TestP311NormalizeZeroFallsBackToEqual`).
- Each weight genuinely moves the composite in its intended direction (latency, health, cost, capability dominance tests) (`TestP311WeightsInfluenceScores`).
- Single-weight flip: identical candidates with a health-vs-latency tradeoff flip winner when the latency weight goes 10 → 80 (normalized) — the exact Phase 4 acceptance case (`TestP311SingleWeightChangeFlipsWinner`).
- All 8 active modes are active; 7 distinct weight vectors. **Planning and long_horizon intentionally share weights {40,10,5,45}** and are differentiated by bonuses (planning: tool-calling+reasoning; long_horizon: context-capacity) and hard filters (long_horizon: context). Not an aliasing bug (`TestP311ModeProfilesHaveDistinctNormalizedWeights`).
- Note: the legacy `TestFastModeDiffersFromDefault` does NOT actually flip winners (both modes pick the same provider in its setup); the new `TestP311FastVsDefaultCanDiffer` is the real proof.

## 5. Bonus Interaction Proofs

- Bonuses change scores in the intended direction; contribution bounded (agentic max 0.04 ≪ base gap used) (`TestP311BonusesAffectScores`).
- Without a demanded capability, a rich candidate scores identical to a plain one — bonuses only apply where configured (`TestP311BonusesAffectScores`).
- Max bonuses cannot overturn a large legitimate base-score gap (fast profile: 0.86 vs ~0.2) (`TestP311BonusCannotBeatLargeBaseGap`).
- Removed dead `bonuses` parameter/branches from `Scorer.buildFactors` (never invoked with non-zero bonuses) to prevent future double-counting.

## 7. Hard-Filter Correctness Proofs

- **Vision is a hard filter** (P3.11 bug #1, fixed): a non-vision provider is rejected before scoring whenever the request contains an actual image; latency/cost/bonus advantages cannot rescue it. Verified for the auto discovery path, the explicit-route path, and the pipeline (`TestP311VisionHardFilterRegression`, `TestP311VisionHardFilterExplicitRoutes`).
- Hard filters fire in both selection paths (discovery + routes) with identical reasons.
- Filter precedence when a candidate violates several requirements (vision + context + R+T) — first matching reason recorded, always rejected (`TestP311HardFilterPrecedence`).
- Circuit-breaker open hard-rejects even when the breaker pool is wired through the pipeline (`TestP311BreakerHardFilterThroughPipeline`).
- **Floating-point noise cannot defeat determinism** (P3.11 bug #2, fixed): scores within `scoreEpsilon = 1e-9` are ties resolved by provider-name tie-break. Regression scenario: cost differing by ~8e-11 in score must pick `alpha`, not the noise-favored `zzz-fp` (`TestP311FPTieBreakRegression`).
- Bonus cannot outweigh a hard filter: rejected candidates are excluded before bonus/score comparison (`TestP311HardFilterCannotBeOutweighedByBonus`).
- Exceptions are documented intentional behavior: unhealthy state is a soft 0.1, breaker-open is the only state-based hard rejection.

## 8. Telemetry Precedence Proofs

- Model-level telemetry overrides provider-level whenever the model entry exists (`TestP311ModelTelemetryOverridesProvider`).
- A present-but-insufficient model entry (2 samples) stays neutral AND blocks provider-level fallback — a great provider history cannot leak in (`TestP311PartialModelTelemetryBlocksProviderFallback`).
- Provider-level fallback applies only when no model entry exists at all (`TestP311TelemetryProviderFallbackWhenModelAbsent`).
- Isolation of same model across providers and same provider across models already covered (`TestSameModelDifferentProvidersIsolated`, `TestSameProviderDifferentModelsIsolated`).

## 9. Fallback Execution Semantics

Verified by inspection of `handler.go` and the existing `TestDecisionPipelineExecutionFallbackPreserved`:
- Primary selected route executes first; on failure, fallback routes execute in order.
- Telemetry records primary-failure and fallback-success/failure per model with retry count; fallback excludes the selected provider; no second routing decision occurs.
- Routing picks the candidate set once; execution is a separate concern.

## 10. Context Budget Audit

- Estimator: 4 tokens/message overhead + conservative `(len+3)/4` per text + 5 per image part + 8 + definition text per tool + 4 per reasoning control + full `thinking_budget`; output = `MaxTokens` when positive, else `DefaultMaxTokens = 4096`.
- Proportionality: even a tiny request rejects a 4096-context candidate (4101 estimate) while 8192 passes (`TestP311ContextFilterProportional`).
- `MaxTokens` participates: 256 output budget accepts 16k candidate; 16384 rejects it (`TestP311MaxTokensOverrideAffectsRequirement`).
- `ThinkingBudget` participates (`TestP311ThinkingBudgetAffectsRequirement`).
- `response_format` does NOT consume context — structured-output requests aren't penalized (`TestP311ResponseFormatDoesNotConsumeContext`).
- Boundary is inclusive: 4100 == 4100 accepted, 4101 > 4100 rejected (`TestP311SlightlyBelowRejectedExactlyEqualAccepted`); exact-boundary, unknown-context, and model-specific variants already covered by `long_horizon_test.go` / `context_estimation_test.go`.

## 11. Vision & Multimodal Semantics

- The vision hint is set ONLY by an actual `ContentPartImageURL` with non-empty URL — not by mode and not by text mentioning images (`ExtractCapabilityHint`).
- `mode=vision` without image content is a weight preference (Capability 25), not a filter: text-only providers stay eligible and a selection always exists (`TestP311VisionModeWithoutImageNoHardReject`).
- Text that merely mentions an image (even a data-URI-looking string) does not trigger the filter (`TestP311TextMentionOfImageNotMultimodal`).
- Actual image → hard filter regardless of mode (Section 7).

## 12. Public API Contract

- Modes are case-sensitive: `"AUTO"`, `"Vision"`, `"FAST"`, `"Long_Horizon"` are invalid (`TestP311UppercaseModeInvalid`).
- Whitespace-padded modes are rejected, not trimmed (`TestP311WhitespaceModeInvalid`).
- The pipeline surfaces the same invalid-mode error (`TestP311PipelineRejectsUppercaseMode`; handler returns 400 `invalid_request`/`param=mode` per `TestHandlerInvalidModeReturnsBadRequest`).
- Exactly the 8 documented strings parse to 8 distinct canonical modes (`TestP311ExactPublicModeStringsAccepted`).
- Empty string parses to `ModeDefault` and the classifier runs; explicit mode overrides classifier intent; `elite` is internal-only (existing tests).

## 13. Determinism & Coherence

- Auto/discovery candidates are sorted by provider name before scoring; ties resolve alphabetically (`selectBestProviderWithMode`).
- Explicit candidate sets preserve route order; order matters ONLY on exact ties (`TestP311ReorderingExplicitCandidates`).
- `scoreEpsilon` fix (Section 7) removes last-bit noise from tie resolution.
- Exactly one `RuntimeSnapshot` per decision: CandidateStage now uses `GetProviderScoresWithSnapshot(hint, dc.RuntimeSnapshot())` (P3.11 bug #3, fixed); `GetProviderScores` delegates. Snapshot coherence under mutation already covered (`TestModeSnapshotCoherence`, `TestTelemetryUsesSinglePipelineSnapshot`).

## 14. End-to-End Pipeline Integrity

- Full pipeline: auth → route → mode profile → capability hint → single snapshot → scoring → hard filters → selection → fallback execution → telemetry. Verified end-to-end in router tests and handler tests; the handler forwards resolved mode and the pipeline re-resolves profiles per request.
- CandidateStage display scores may disagree with final selection (display path applies no mode hard filters); SelectionStage is authoritative — documented, cosmetic-only.

## 15. Cache & Mode Interaction

- `buildCacheKey` includes `mode`, so cached responses can never bypass mode routing semantics (`TestP311CacheKeyModeIsolation`).
- Omitted mode vs explicit `"auto"` produce distinct keys — they are distinct API inputs (`TestP311CacheKeyOmittedVsExplicitAuto`).
- Key uses the resolved provider model ID: different upstream models never share entries; different request aliases resolving to the same model do share (correct) (`TestP311CacheKeyResolvedModelID`).
- Capability-affecting fields (tools, reasoning params, response_format, image content) all participate (`TestP311CacheKeyCapabilityFields`).
- Known limitation (documented, not fixed): key is namespaced by provider model ID only, so the same model ID served by two providers collides. Mode cannot cause staleness across modes; provider-level collisions are theoretical for identical model IDs.

## 17. Invariant Verification

- Adding a worse candidate never changes the winner (`TestP311AddingWorseCandidateCannotChangeWinner`).
- Removing the winner selects the best remaining (`TestP311RemovingWinnerSelectsBestRemaining`).
- Reordering explicit candidates only affects ties (`TestP311ReorderingExplicitCandidates`).
- Hard-rejected candidates are never selected, even when sole candidate; `Selected` is never set on a rejected score (`TestP311HardRejectedNeverSelected`).
- Mode profiles are per-call copies; mutating one decision's profile cannot leak (`TestP311ModeProfileMutationIsolation`).
- Single-candidate sets stay pinned (existing `TestOneCandidateRemainsPinned`); snapshot coherence (existing).

## 18. Performance & Complexity Verification

- Scoring is O(n) over candidates with a single `registry.All()` pass; no nested provider scans.
- `getCostPerToken` is a map lookup on a static config map (provider `pricingFunc`, no network/RPC) — confirmed no I/O in the decision hot path; no caching per candidate (micro-inefficiency, documented).
- Capability lookups are cached on the engine (`modelCaps`/`providerCaps` maps, RWMutex).
- Telemetry preference is O(1) per candidate from the snapshot; no extra snapshots.
- No goroutines or locks held across decisions in the selection path; runtime store uses atomics + short RW locks.

## 20. Intentional Behavior Documented (no fix)

- **Planning ≡ long_horizon weight profile** {40,10,5,45}; differentiated by bonuses + hard filters (Section 4).
- **ContextCapacity bonus is binary**: triggers on any `MaxContext > 0`, not scaled by capacity — large-context models get no extra credit within a mode. Long horizon's hard filter already enforces minimums.
- **Unhealthy (0.1) is a soft penalty**, not a hard rejection; breaker-open is the hard state rejection. Sole unhealthy candidate still serves the request.
- **Partial model telemetry blocks provider fallback** (Section 8) — intentional precedence, potential availability tradeoff.
- **Provider-level telemetry is a superset** — model records also bump provider counters (pre-existing, verified by `TestProviderModelTelemetryIsolation`).
- **CandidateStage display scores lack hard filters** — cosmetic divergence from SelectionStage, which is authoritative.
- **Cache key collision** for identical model IDs across providers (Section 15).
- **`ParseMode` is case-sensitive and does not trim** — documented API contract (Section 12).
- **Per-candidate `GetPricing` map lookup, no caching** — safe (static map) but repeated per decision.
- Legacy `TestFastModeDiffersFromDefault` doesn't actually flip winners; `TestP311FastVsDefaultCanDiffer` is the real proof.

## 23. Residual Risks & Limitations

- Token estimation is a heuristic (4 chars/token); dense scripts and long outputs can underestimate — the 4096 default output budget keeps the bound conservative, not exact.
- Cache-key provider collision (Section 15) is unaddressed by design (would require adding provider to the key, changing existing cache entries).
- Exact tie behavior at `scoreEpsilon` boundary: two scores differing by <1e-9 are intentional ties; legitimate sub-1e-9 differences are indistinguishable — acceptable for a score model.
- The `nvidia_nim` style catalogs (see AGENTS.md) can advertise unreachable models; probes are out of scope for P3.11.
- Production Dockerfile uses `CGO_ENABLED=0`; SQLite driver requires CGO (pre-existing deployment caveat, unchanged).

## 24. Recommendations

1. Scale the `ContextCapacity` bonus by `MaxContext` (e.g. log-scale or tiered) so long-context models get proportional credit.
2. Include the provider name in the cache key to eliminate cross-provider collisions for identical model IDs.
3. Cache `getCostPerToken` results per (provider, model) since pricing is a static map.
4. Add `ExecutionPreferenceScore` to `CandidateScore` for dashboard transparency of telemetry contributions.
5. Retire the legacy `TestFastModeDiffersFromDefault` or fix its setup so it actually flips.
