# P3.8 Planning Mode Activation — Report

## 1. Existing P3.7 Telemetry Audit

### Consumed Signals from `runtime.ProviderStateSnapshot`

| Field | Scope | Derivation |
|-------|-------|------------|
| `ExecutionCount` | Provider-level | Cumulative atomic counter |
| `ExecutionSuccessCount` | Provider-level | Cumulative atomic counter |
| `ExecutionFailureCount` | Provider-level | Cumulative atomic counter |
| `ToolCallSuccessCount` | Provider-level | Cumulative atomic counter |
| `ToolCallFailureCount` | Provider-level | Cumulative atomic counter |
| `RetryCount` | Provider-level | Cumulative atomic counter |

**Attribution level**: Provider-name only (per P3.7 design). No provider+model sub-counters exist.

### Minimum Sample Threshold

**Chosen constant**: `minExecutionSample = 5`

Rationale:
- Small enough to start observing after a handful of real requests
- Large enough to distinguish signal from noise for binary outcomes
- Consistent with the existing "unknown = neutral" semantics in the scorer

### Derived Rates

```
execution_success_rate = ExecutionSuccessCount / (ExecutionSuccessCount + ExecutionFailureCount)
tool_success_rate      = ToolCallSuccessCount / (ToolCallSuccessCount + ToolCallFailureCount)
retry_rate             = RetryCount / ExecutionCount
```

All rates are `NaN`-free: when the denominator is 0, the rate branch is skipped entirely.

## 2. Planning Capability Requirements

### HARD REQUIREMENTS

1. **Reasoning** — provider must advertise `Capabilities.Reasoning == true`
2. **ToolCalling** — provider must advertise `Capabilities.ToolCalling == true`

These are enforced as a **hard filter** in both `selectBestProviderWithMode` and `selectFromRoutesWithMode`, following the same pattern as Long Horizon's context hard filter.

### SOFT PREFERENCES

1. Execution success/reliability
2. Tool-call success/reliability
3. Low retry rate
4. Context headroom (via existing Long Horizon infrastructure)
5. Runtime health
6. Reasonable latency
7. Cost (lower priority)

## 3. Hard vs Soft Requirements

| Requirement | Type | Enforcement |
|-------------|------|-------------|
| Reasoning capability | Hard | Reject candidate if `!caps.Reasoning` |
| ToolCalling capability | Hard | Reject candidate if `!caps.ToolCalling` |
| Context adequacy | Hard | Reuses existing Long Horizon filter when `ModeLongHorizon` is active |
| Execution reliability | Soft | Adds preference bonus/penalty in `[-0.10, +0.10]` |
| Tool reliability | Soft | Adds preference bonus/penalty in `[-0.04, +0.04]` |
| Retry behavior | Soft | Adds penalty when retry rate exceeds threshold |
| Health | Soft | Existing health scoring (unchanged) |
| Latency | Soft | Existing latency scoring (unchanged) |
| Cost | Soft | Existing cost scoring (unchanged) |

## 4. Cold-Start / Unknown Telemetry Semantics

| Condition | Counter Values | Interpretation | Score Contribution |
|-----------|---------------|----------------|-------------------|
| No data | `ExecutionCount == 0` | Unknown | 0.0 (neutral) |
| Insufficient sample | `0 < ExecutionCount < 5` | Insufficient | 0.0 (neutral) |
| Measured good | `ExecutionCount >= 5`, `execRate >= 0.80` | Good | Positive bonus |
| Measured poor | `ExecutionCount >= 5`, `0 < execRate < 0.80` | Poor | Negative penalty |
| All failed | `ExecutionCount >= 5`, `execRate == 0` | Poor | Negative penalty |

**Key invariant**: Zero counts remain distinguishable from measured failure because the counters start at 0 and only increment on actual events. The `executionTelemetryPreference` function checks `ExecutionCount > 0` before computing any rate.

Tool-call telemetry uses the same `minExecutionSample = 5` gate independently.

## 5. Execution Reliability Calculation

```go
execRate := float64(ps.ExecutionSuccessCount) / float64(ps.ExecutionSuccessCount+ps.ExecutionFailureCount)
```

Thresholds:
- `goodExecRate = 0.80`
- Bonus: `+0.05 * (execRate - 0.80 + 0.20)` → max +0.06
- Penalty: `-0.05 * (0.80 - execRate)` → min -0.04

## 6. Tool-Call Reliability Calculation

```go
totalToolCalls := ps.ToolCallSuccessCount + ps.ToolCallFailureCount
toolRate := float64(ps.ToolCallSuccessCount) / float64(totalToolCalls)
```

Thresholds:
- `goodToolRate = 0.70`
- Bonus: `+0.03 * (toolRate - 0.70 + 0.20)` → max +0.036
- Penalty: `-0.03 * (0.70 - toolRate)` → min -0.021

**Independent of execution count**: Tool-call telemetry is computed regardless of whether execution count meets the sample threshold. This reflects the fact that tool-call history may exist even when execution history is sparse.

## 7. Retry Preference Calculation

```go
retryRate := float64(ps.RetryCount) / float64(ps.ExecutionCount)
```

Only applied when `ExecutionCount >= minExecutionSample`.

Threshold:
- `maxRetryRate = 0.30`
- Penalty: `-0.03 * (retryRate - 0.30) / 0.70` → max -0.03

## 8. Context Interaction

Planning **composes** with Long Horizon context enforcement but does not duplicate it. When `mode=planning` is active:

1. The Planning hard filter checks Reasoning + ToolCalling
2. If the request also has a context requirement (from explicit `mode=long_horizon` or classifier), the existing Long Horizon filter applies on top
3. Planning does NOT independently compute context requirements — it reuses the existing `EstimateRequestTokens` + hard filter path

This composition is verified by `TestPlanningUsesContextRequirement`.

## 9. Model/Provider Attribution

Per P3.7 design, all telemetry is attributed at the **provider name** granularity:

- `ExecutionCount`, `ExecutionSuccessCount`, etc. are keyed by provider name in `RuntimeSnapshot`
- No provider+model sub-counters exist
- The `executionTelemetryPreference` method reads from `snapshot.Providers[providerName]`

**Limitation acknowledged**: Provider A's execution history is attributed to all models on that provider. For Planning routing, this is acceptable because:
1. Planning requires reasoning + tool-calling capabilities which are provider-level advertisements
2. The preference is soft (bounded ±0.10) and only influences tie-breaking among equally-qualified candidates
3. Model-specific capability filtering (hard filter) is still enforced independently

## 10. Mode Profile and Scoring Changes

### ModeProfile for Planning

```go
ModePlanning: {
    Mode:   ModePlanning,
    Active: true,
    WeightPreferences: &RoutingWeightPreferences{
        Health:     40,
        Latency:    10,
        Cost:       5,
        Capability: 45,
    },
    CapabilityBonuses: CapabilityBonuses{
        ToolCalling: 0.20,
        Reasoning:   0.25,
    },
}
```

### Scoring Architecture

The existing scoring architecture is extended, not replaced:

```
CompositeScore = existing weighted score
               + mode capability bonuses (Reasoning +0.25, ToolCalling +0.20)
               + execution telemetry preference (±0.10)
               + tool telemetry preference (±0.04)
               - retry penalty (up to -0.03)
```

The mode-specific weights (Health=40, Latency=10, Cost=5, Capability=45) are normalized per-decision and do not mutate global RouterEngine weights.

### Constants

```go
const (
    minExecutionSample int64 = 5
    goodExecRate       float64 = 0.80
    goodToolRate       float64 = 0.70
    maxRetryRate       float64 = 0.30
)
```

## 11. RuntimeSnapshot Flow

1. `DecisionPipeline.Execute()` acquires ONE snapshot via `runtimeMgr.Snapshot(ctx)`
2. Snapshot is stored in `DecisionContext.runtimeSnap`
3. `SelectionStage` passes the same snapshot to `RouterEngine.selectBestProviderWithMode()`
4. `scoreCandidateWithMode()` derives all operational state from the snapshot
5. `executionTelemetryPreference()` reads execution counters from the snapshot

**Invariant preserved**: Exactly one `RuntimeSnapshot` per pipeline execution.

## 12. Explicit Route/Fallback Semantics

### Explicit model/route + mode=planning

- Candidates are constrained to the explicitly supplied set
- Planning hard filter rejects unqualified candidates within that set
- If the single candidate lacks Reasoning or ToolCalling: **rejected**, not silently expanded
- If a fallback in the candidate set satisfies Planning: **fallback wins**

### Auto mode + mode=planning

- All registered providers are considered
- Planning hard filter rejects non-qualifying providers
- Remaining providers are scored with telemetry preferences

### Single candidate pinned

- If exactly one candidate satisfies Planning requirements: it remains effectively pinned
- If exactly one candidate does NOT satisfy Planning requirements: returns empty selection

These semantics are verified by:
- `TestPlanningExplicitRouteConstraint`
- `TestPlanningFallbackCanWin`
- `TestPlanningSingleCandidatePinnedWhenQualified`
- `TestPlanningSingleCandidateRejectedWhenUnqualified`

## 13. Trace Changes

No trace schema changes were made. The existing `DecisionTrace` architecture captures:
- `resolved_mode` and `mode_source` in the intent stage event
- Candidate rejection reasons in the trace
- Runtime snapshot hash (includes execution telemetry since P3.7 added the fields to `ProviderStateSnapshot`)

Planning-specific trace metadata flows through the existing stage result metadata where supported.

## 19. Agentic Status

`mode=agentic` remains **inactive**:

## 20. Remaining Limitations

1. **Provider-only telemetry attribution**: Execution history is at provider-name granularity, not provider+model. This is a P3.7 design limitation, not a P3.8 regression.

2. **Cumulative (not rolling) counters**: Telemetry accumulates indefinitely. For production use, a rolling window or TTL-based decay would be preferable. Out of scope for P3.8.

3. **No synthetic confidence score**: Per instructions, no "planning-quality score" was invented. Only observable signals from P3.7 telemetry are used.

4. **Handler fallback for inactive modes**: When the pipeline rejects an inactive mode, the handler falls back to legacy resolution rather than returning a 400. This is existing behavior and was not changed.

5. **Classifier does not emit Planning mode**: The keyword-based classifier (`ClassifyRequest`) does not currently classify requests as `ModePlanning`. Planning must be requested explicitly via `mode=planning`. This is intentional — Planning is a deliberate user choice, not an automatic inference.
