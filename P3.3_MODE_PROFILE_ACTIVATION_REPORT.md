# P3.3 Mode Profile Activation Report

## 1. Before Behavior

- `ModeProfile` struct existed in `internal/router/mode_profile.go` but `DefaultModeProfiles()` returned empty profiles with no weight preferences or capability bonuses.
- `WeightPreferences` was never read anywhere in the codebase — it did not reach `RouterEngine`.
- `DecisionContext` had no `modeProfile` or `effectiveWeights` fields.
- `RouterEngine` used only global `config.RoutingWeights` stored in `Scorer`; there was no per-decision weight mechanism.
- `pipeline_stages.go` used an inline `classifyIntent()` function and did not derive mode profiles.
- `selection.go` used legacy `healthStore`/`metricsStore` directly for health and latency; it did not use `runtime.RuntimeSnapshot`.
- No `SelectFromRoutes`, `SelectFromRoutesWithSnapshot`, `mergeModelOverrides`, `LoadCatalogCapabilities`, or `SetModelCapabilities` methods existed.
- Mode classification affected `policy.Intent.TaskType` but had no impact on provider scoring.

## 2. After Behavior

- Each mode now has explicit `WeightPreferences` and `CapabilityBonuses` that meaningfully influence routing.
- The `IntentStage` derives the `ModeProfile` from canonical classification and stores it (plus normalized effective weights) in `DecisionContext`.
- `RouterEngine` accepts per-decision weights and bonuses via new internal methods; global weights are never mutated.
- `selection.go` now uses `runtime.RuntimeSnapshot` as the single authoritative source for health/latency/error-rate.
- Added `SelectFromRoutes`, `SelectFromRoutesWithSnapshot`, model-level capability caching, and catalog integration.
- `BuildConfigSnapshot` added to legacy `Engine` for handler compatibility.
- All 128 router tests pass, including 23 new mode-specific behavior tests.

## 3. Mode Profile Architecture

```
CanonicalClassifier.ClassifyRequest(text) → CapabilityProfile{Mode, Confidence}
        ↓
IntentStage.Execute()
        ↓
modeProfileForMode(profile.Mode) → *ModeProfile
        ↓
DecisionContext.SetModeProfile(mp)
DecisionContext.SetEffectiveWeights(mp.effectiveWeights())
        ↓
CapabilityStage.Execute() → CapabilityRequirement (unchanged)
        ↓
CandidateStage.Execute()
  → reads dc.EffectiveWeights() + dc.ModeBonuses()
  → calls engine.scoreCandidateFromRouteWithMode(ctx, route, hint, snap, weights, bonuses)
        ↓
SelectionStage.Execute()
  → reads dc.ModeProfile()
  → calls engine.selectFromRoutesWithMode(ctx, candidates, req, snap, mp)
        ↓
RouterEngine scoring
  → Scorer.CompositeScoreWithBonuses(c, capHint, weights, bonuses)
  → base composite + prefWeight * sum(mode-relevant bonuses)
```

## 4. Per-Decision Weight Flow

```
Global config weights (RoutingWeights)
        ↓
DefaultModeProfiles()[mode].WeightPreferences (RawWeights)
        ↓
Normalize() → Weights (immutable, per-decision)
        ↓
stored in DecisionContext.effectiveWeights
        ↓
passed to RouterEngine scoring methods
        ↓
NOT stored in RouterEngine (no cross-request state)
```

## 5. Fast Mode

**Weights:** Health=55, Latency=40, Cost=3, Capability=2 → normalized: 0.55, 0.40, 0.03, 0.02

**Behavior:**
- Latency weight increases from 25% (default) to 40%.
- Health weight increases from 40% to 55% to prevent selecting broken endpoints.
- Capability weight drops to 2% (nearly negligible).
- A provider with terrible error rate (high errorPenalty in healthScoreFromSnapshot) will still score low even if its latency is excellent.
- No capability bonuses are applied.

**Tests:**
- `TestFastModePrefersLowerLatency` — same health, different latency → fast wins
- `TestFastModeDoesNotSacrificeHealth` — low latency but unhealthy → healthy wins
- `TestFastModeDiffersFromDefault` — latency tradeoff produces different selection

## 6. Coding Mode

**Weights:** Health=25, Latency=10, Cost=5, Capability=60 → normalized: 0.25, 0.10, 0.05, 0.60

**Bonuses:** ToolCalling=0.25, Reasoning=0.15, Structured=0.10

**Behavior:**
- Capability weight dominates at 60%.
- Providers with ToolCalling get +0.25 preference score (weighted by 5% prefWeight = +0.0125 to total).
- Providers with Reasoning get +0.15 preference score.
- ToolCalling is a SOFT preference — providers without it are NOT rejected.
- Coding requests without explicit tool usage still benefit from tool-calling-capable providers.

**Tests:**
- `TestCodingModePrefersToolCalling` — equal health/latency, with-tools wins
- `TestCodingModePrefersReasoning` — equal health/latency, has-reason wins
- `TestCodingModeDoesNotRejectNonToolCalling` — plain provider still selected when only option

## 7. Reasoning Mode

**Weights:** Health=20, Latency=10, Cost=5, Capability=65 → normalized: 0.20, 0.10, 0.05, 0.65

**Bonuses:** Reasoning=0.35

**Behavior:**
- Strongest capability emphasis at 65%.
- Reasoning-capable providers get a +0.35 preference bonus.
- Non-reasoning providers are NOT hard-rejected.
- The existing `matchScore` soft penalty for missing reasoning (0.3 factor score) remains as a baseline.

**Tests:**
- `TestReasoningModePrefersReasoningProvider` — reasoning provider wins on equal footing
- `TestReasoningModeDoesNotHardReject` — non-reasoning provider still selected when only option

## 8. Vision Mode

**Weights:** Health=40, Latency=20, Cost=15, Capability=25 → same as default

**Behavior:**
- Vision is already a HARD filter via `matchScore` returning 0.0 when `hint.Vision && !caps.Vision`.
- Mode profile weights are identical to default because the hard filter already enforces vision capability.
- No capability bonuses needed — the hard filter is sufficient.

**Hard vs Soft Semantics:**
- HARD: `hint.Vision = true` (actual image content present) → non-vision providers score 0.0
- SOFT: keyword "image" in text WITHOUT actual image content → does NOT trigger hard rejection

**Tests:**
- `TestVisionModeRejectsNonVisionProvider` — actual image content → non-vision rejected
- `TestVisionModeSelectsVisionProvider` — both vision providers eligible
- `TestVisionKeywordWithoutImageDoesNotTriggerHardReject` — text mentioning "image" but no image content → text-only provider accepted

## 9. Auto / Default

**Weights:** Health=40, Latency=25, Cost=15, Capability=20 (explicitly defined, matches global defaults)

**Behavior:**
- Baseline behavior preserved.
- No capability bonuses.
- Uses standard normalization and scoring.
- `ModeElite` has empty profile (deferred per spec).

**Tests:**
- `TestDefaultModePreservesBaselineBehavior` — same selection as pre-P3.3
- `TestAutoModePreservesBaselineBehavior` — deterministic tie-break preserved

## 10. Explicit Model / Route Semantics

- **Explicit model**: When a specific model ID is given, the candidate set is constrained to providers supporting that model. Mode preferences score within that set but cannot expand it.
- **Explicit route**: When pre-resolved routes are passed to the pipeline, mode preferences affect scoring among those routes only. No external providers are discovered.
- **One candidate**: Remains effectively pinned regardless of mode.
- **Tie-breaking**: Alphabetical/provider-order tie-breaking is preserved.

**Tests:**
- `TestModePreferencesOnlyAffectSuppliedCandidates` — mode cannot discover providers outside candidate set
- `TestModeDoesNotExpandCandidateSet` — explicit route with one candidate stays pinned
- `TestOneCandidateRemainsEffectivelyPinned` — all modes preserve single-candidate pinning
- `TestEqualScoreDeterministicTieBreaking` — tie-break order unchanged
- `TestModeSnapshotCoherence` — mode routing still uses ONE snapshot per decision
- `TestModeWeightsArePerDecision` — global weights are never mutated

## 13. Deferred Modes

**Planning, Agentic, Long Horizon** remain deferred because:
- The spec explicitly states "Do NOT implement: Planning, Agentic, Long Horizon yet."
- These modes require semantic understanding beyond keyword heuristics (e.g., multi-step task decomposition, autonomy metrics, sustained reliability tracking).
- The `ModeElite` profile exists as a placeholder but has no weight preferences or bonuses configured.
- The infrastructure (mode profile → decision context → scoring) is in place; activation can happen in a future phase when the semantic classifiers are ready.

## 14. Remaining Architecture Debt

**Genuine P1/P2 items:**
- `trace_test.go` and `task/v25_test.go` call `pipeline.Execute` with 4 arguments instead of 5 — these are pre-existing test mismatches from the P3.2 transition, not caused by P3.3 changes.
- The inline `classifyIntent()` in the original `pipeline_stages.go` was replaced by the canonical `ClassifyRequest()` from `classifier.go`; the old function is now unused but kept for backward compatibility in case external consumers reference it.
- `healthStore` and `metricsStore` fields remain on `RouterEngine` for backward compatibility but are no longer the primary scoring path — the `RuntimeSnapshot`-based path takes precedence when available.
