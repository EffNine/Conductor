# P4.1 Failure Taxonomy Foundation — Report

**Status:** COMPLETE
**Date:** 2026-08-22
**Scope:** `internal/failure` (new), `internal/provider`, `internal/handler` (observability only)

---

## 1. Executive Summary

P4.1 introduces the canonical failure taxonomy every future reliability layer
(retry engine, classification-aware breakers, fallback ordering, analytics)
will consume. Every failed provider attempt can now be classified exactly
once into one of eight canonical classes, with policy metadata attached.

The change is **observability-first**: classification is produced and logged,
but no component acts on it yet. Retry logic, breaker semantics, routing
scores, fallback execution, and analytics endpoints are explicitly untouched.

## 3. Architecture Decisions

1. **Classification is central, not distributed.** A single pure function
   (`failure.Classify`) maps any error to `(Class, suggestedBackoff)`. Adapter
   boundaries only *enrich* (capture `Retry-After`); they do not classify.
   This keeps adapters dumb and lets policy evolve in one place.
2. **Existing `ProviderError.Type` constants are preserved as the primary
   signal.** The six pre-existing constants map deterministically onto the new
   classes; unknown type strings fall back to status-code heuristics so every
   current error path yields a class without touching adapter call sites.
3. **`Retry-After` is advisory data, never behavior.** Nothing reads it today;
   P4.2's retry engine will honor it.
4. **Class-level policy vs instance-level hint are separated.** `PolicyFor`
   answers "how should reliability layers treat this class?" statically;
   `pe.RetryAfter` carries the server's actual advice when present.
5. **Dependency direction:** `failure → provider` only. No router, handler, or
   breaker imports flow into the taxonomy package; no import cycles are
   possible.

## 4. Classification Matrix

| Class | Primary signals | Retryable | Breaker impact | Backoff hint supported |
|---|---|---|---|---|
| `rate_limited` | 429 / `rate_limit_error` / `RESOURCE_EXHAUSTED` | yes | `throttle_only` | yes |
| `timeout` | deadline exceeded, net timeout inside transport failure | yes | `count` | no |
| `auth_failed` | 401/403 / `authentication_error` / `permission_error` | no | `none` | no |
| `capacity` | 503 / overloaded 529 | yes | `count` | yes |
| `upstream_error` | other 5xx | yes | `count` | no |
| `network_error` | connection-level transport failures | yes | `count` | no |
| `invalid_request` | 400-class 4xx incl. context length | no | `none` | no |
| `unknown` | anything unattributable | no | `count` | no |

Note: `throttle_only` is recorded but **not yet consumed** — breakers still
count rate limits as failures until P4.3 changes that deliberately.
