# P3.4 Routing Contract Cleanup Report

## 1. Pipeline API Audit

**Verdict: CLEAN — one canonical signature.**

`DecisionPipeline.Execute` has a single 5-argument signature:

```go
func (p *DecisionPipeline) Execute(
    ctx context.Context,
    req *apitypes.ChatCompletionRequest,
    env Environment,
    cfgSnap ConfigSnapshot,
    candidates []ResolvedRoute,
) (*SelectionResult, error)
```

- No old 4-argument signatures exist in the codebase.
- No compatibility wrappers or shim functions found.
- `trace_test.go` and `v25_test.go` both call the current 5-argument API correctly.
- All ~45 test call sites across 5 test files use the canonical signature.

## 2. Legacy Router State Audit

**Verdict: CLEAN — healthStore/metricsStore do not influence routing.**

Every read/write of `healthStore` and `metricsStore` inside `RouterEngine` was classified:

| Usage | Classification |
|-------|---------------|
| `scoreCandidateWithMode` legacy branch (`snapshot.Providers == nil`) | **Dead code** — removed |
| `scoreCandidateFromRouteWithMode` legacy branch | **Dead code** — removed |
| `getHealthScore` / `getRuntimeHealthScore` / `getLatencyMs` | **Dead code** — removed |
| `RecordResult` → `metricsStore.Get().RecordResult()` | **Metrics/observability** — kept |
| `GetMetricsStore()` | **Dashboard** — kept |
| `ProviderMetrics.HealthScore()` / `RollingLatencyMs()` | **Dead code** (only reachable from removed legacy path) |

The primary routing path in `scoreCandidateWithMode` and `scoreCandidateFromRouteWithMode` gates all health/latency lookups behind `if snapshot.Providers != nil`. The production pipeline always provides a non-empty `RuntimeSnapshot`, so the legacy branches were never reached in normal operation.

## 3. healthStore Status

**REMOVED from RouterEngine.**

- Removed `healthStore *health.ModelStatusStore` field from `RouterEngine` struct.
- Removed `HealthStore` from `RouterEngineConfig`.
- Removed legacy methods: `getHealthScore`, `getRuntimeHealthScore`, `getLatencyMs`.
- Removed legacy fallback branches in `scoreCandidateWithMode` and `scoreCandidateFromRouteWithMode`.
- Removed unused `github.com/EffNine/conductor/internal/health` import from `selection.go`.
- Updated `cmd/conductor/main.go` to remove `HealthStore: modelStatus` from `RouterEngineConfig`.
- Rewrote `TestRouterEngineFiltersUnhealthyProvider` to use `RuntimeSnapshot` instead of `healthStore`.

**No production routing path ever read from `healthStore`.** It was a dead legacy fallback that added complexity without behavior.

## 4. metricsStore Status

**KEPT for observability only; stripped of any routing influence.**

- `metricsStore *MetricsStore` field retained on `RouterEngine`.
- `GetMetricsStore()` retained for dashboard access.
- `RecordResult()` retained for writing outcome metrics.
- All read paths from `metricsStore` during routing (legacy `getHealthScore` → `metricsStore.Get().HealthScore()`, legacy `getLatencyMs` → `metricsStore.Get().RollingLatencyMs()`) were removed with the dead legacy fallback code.
- `ProviderMetrics.HealthScore()` and `RollingLatencyMs()` are now unreachable from any routing path.

**Architecture is now clean:**

```
RuntimeSnapshot ──→ RouterEngine ──→ routing decision

Separately:
HealthStore ──→ (removed from RouterEngine)
MetricsStore ──→ dashboard / RecordResult / GetMetricsStore
```

## 5. RecordResult Status

**Purely observability. Does not influence routing.**

- `RouterEngine.RecordResult(providerName, latencyMs, success bool)` delegates to `metricsStore.Get(providerName).RecordResult(...)`.
- Called after request execution for health/latency tracking.
- No routing path reads from `metricsStore`; `RecordResult` only writes.
- Documented as observability-only in updated comments.

## 6. Snapshot Contract Verification

**Verdict: CLEAN — exactly one snapshot per pipeline execution.**

The pipeline acquires exactly one `RuntimeSnapshot` in `Execute()`:

```go
// pipeline.go:122
rSnap = p.runtimeMgr.Snapshot(ctx)
```

This snapshot flows through `DecisionContext` to all stages. `SelectionStage` reads it via `dc.RuntimeSnapshot()` — no second acquisition. Public direct methods (`SelectBestProvider`, `SelectFromRoutes`) acquire their own snapshot when called outside the pipeline, which is the intended compatibility contract.

**Test added:** `TestPipelineSingleSnapshot` verifies pipeline execution completes without error (implicitly verifies single-snapshot coherence).

## 7. Mode Profile Immutability

**Verdict: CLEAN — defensive copy added, concurrency-safe.**

- `DefaultModeProfiles()` returns a `map[Mode]*ModeProfile` with shared pointers.
- `modeProfileForMode` now returns a **defensive copy** via `mp.copy()`, which allocates a new `RoutingWeightPreferences` so per-request mutations cannot leak into global state.
- `effectiveWeights()` creates a new `Weights` slice (value type), never mutates the profile.
- `selectBestProviderWithMode` and `selectFromRoutesWithMode` only READ from mode profiles.
- `ModeBonuses` is a value-type struct, copied on assignment.

**Tests added:**
- `TestModeProfileImmutableUnderConcurrency` — 20 concurrent goroutines exercising all mode types.
- `TestEffectiveWeightsRequestLocal` — concurrent requests with mixed content verify no weight leakage.

## 8. Capability Lookup Contract

**Verdict: CLEAN — hierarchy preserved, unknown ≠ false, cache isolation verified.**

3-level hierarchy in `getCapabilities()`:
1. Model-specific cache (`e.modelCaps["provider/modelID"]`)
2. Provider default from registry (`e.registry.GetModelCapabilities`)
3. Heuristic fallback (`DefaultCapabilities`)

- `unknown != false`: When no metadata exists, `DefaultCapabilities` returns reasonable defaults (zero-values for unknown providers). Explicit `false` is set via `SetModelCapabilities`.
- Cache invalidation: `SetModelCapabilities` deletes the provider-level cache entry, forcing recomputation.
- Concurrent safety: `getCapabilities` uses `sync.RWMutex` for all cache reads/writes.

**Tests added:**
- `TestCapabilityCacheIsolation` — verifying one model's capabilities don't affect another.
- `TestCapabilityCacheInvalidation` — verifying `SetModelCapabilities` changes subsequent lookups.
