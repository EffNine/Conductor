**Status:** COMPLETE

**Author:** Agnes (Sapiens AI)

## 1. Current Telemetry Architecture

Conductor's execution telemetry flows through these layers:

```
Handler/Agent → ExecutionToRuntimeAdapter → RuntimeStore → ProviderRuntimeImpl
                                                        ↓
                                                  ProviderStateSnapshot
                                                        ↓
                                               RuntimeSnapshot
                                                        ↓
                                          executionTelemetryPreference()
                                                        ↓
                                            Agentic / Planning routing
```

### Key Components

| Component | Location | Role |
|-----------|----------|------|
| `ProviderRuntimeImpl` | `internal/runtime/store.go` | Concrete implementation holding atomic counters |
| `ProviderStateSnapshot` | `internal/runtime/types.go` | Point-in-time view of a provider's state |
| `RuntimeSnapshot` | `internal/runtime/types.go` | Aggregate of all provider snapshots |
| `ExecutionToRuntimeAdapter` | `internal/runtime/adapter/execution.go` | Translates execution events to runtime updates |
| `RouterEngine.executionTelemetryPreference()` | `internal/router/selection.go` | Computes routing preference from telemetry |

## 2. Telemetry Signal Inventory

| Signal | Source | Granularity | Attribution | Aggregation Window | Meaning |
|--------|--------|-------------|-------------|-------------------|---------|
| `ExecutionCount` | handler + agent loop | **Provider-level** | ProviderName only | Lifetime (no expiration) | Total chat completion attempts |
| `ExecutionSuccessCount` | Same | Provider-level | ProviderName | Lifetime | Successful chat completions |
| `ExecutionFailureCount` | Same | Provider-level | ProviderName | Lifetime | Failed chat completions |
| `ToolCallSuccessCount` | agent loop | Provider-level | ProviderName | Lifetime | Successful tool calls |
| `ToolCallFailureCount` | Same | Provider-level | ProviderName | Lifetime | Failed tool calls |
| `RetryCount` | handler (fallback) | Provider-level | ProviderName | Lifetime | Total fallback retries consumed |

### P3.10 Addition: Model-Level Signals

| Signal | Source | Granularity | Attribution | Aggregation Window |
|--------|--------|-------------|-------------|-------------------|
| `ModelExecutions[providerModelID]` | handler + agent loop | **Provider+Model** | ProviderName + ProviderModelID | Lifetime |

Model-level data is populated ONLY when `ProviderModelID` is non-empty at emission time. When empty, only provider-level counters are updated.

## 3. Granularity Audit

### Pre-P3.10 (Provider-Only)

All telemetry was recorded and consumed at the **provider level only**. When two candidates shared the same provider but had different models:

```
Candidate A: provider=openai, model=gpt-4o
Candidate B: provider=openai, model=gpt-4o-mini
```

Both received **identical** execution telemetry from `snap.Providers["openai"]`. This was an architectural gap — model-level behavior differences were invisible to routing.

### Post-P3.10 (Provider+Model)

Telemetry is now recorded at both levels:
- **Provider-level**: aggregate across all models (backward compatible)
- **Model-level**: isolated per `ProviderModelID` (new)

Routing prefers model-level when available, falls back to provider-level when not.

## 4. Provider/Model Attribution Audit

### Call Sites (Pre-P3.10)

```go
// handler/handler.go:450
h.recordExecutionTelemetry(resolved.ProviderName, true, 0)  // MISSING modelID

// agent/loop.go:155
a.recordExecutionFinish(resolved.ProviderName, false)       // MISSING modelID
```

### Call Sites (Post-P3.10)

```go
// handler/handler.go:450
h.recordExecutionTelemetry(resolved.ProviderName, resolved.ProviderModelID, true, 0)

// agent/loop.go:155
a.recordExecutionFinish(resolved.ProviderName, resolved.ProviderModelID, false)
```

**Model identity IS available** at every emission point:
- HTTP handler: `resolved.ProviderModelID` from route resolution
- Agent loop: `resolved.ProviderModelID` from task step resolution
- Fallback handlers: `fb.ProviderModelID` from fallback config

### Routing Lookup (Pre-P3.10)

```go
// selection.go — only used providerName
ps, hasState := snap.Providers[providerName]
```

### Routing Lookup (Post-P3.10)

```go
// selection.go — tries model-level first, falls back to provider-level
var es *runtime.ModelExecutionState
if modelID != "" && ps.ModelExecutions != nil {
    if state, ok := ps.ModelExecutions[modelID]; ok {
        es = &state
    }
}
// If es != nil: use model-level counters
// If es == nil: use provider-level counters (original behavior)
```

### Classification of Previous Behavior

**Architectural correctness gap** — not merely "acceptable provider-level signal":
- Two candidates on the same provider with different models received identical telemetry
- A model with 100% success could be masked by another model's failures on the same provider
- The gap was especially problematic for providers like NIM that expose multiple models

## 5. Execution Reliability Semantics

Formalized in `executionTelemetryPreference()` (`selection.go:912`):

```
State           Condition                         Score Effect
─────────────────────────────────────────────────────────────────────
UNKNOWN         ExecutionCount == 0               Neutral (0.0)
INSUFFICIENT    ExecutionCount > 0 && < 5        Neutral (0.0)
MEASURED GOOD   successRate >= 0.80              Positive bonus (up to +0.06×intensity)
MEASURED POOR   0 < successRate < 0.80           Negative penalty (down to -0.04×intensity)
HIGH RETRY      retryRate > 0.30                 Additional penalty (down to -0.03×intensity)
```

**Clamp:** `[-0.10×intensity, +0.10×intensity]`

### Constants

```go
const (
    minExecutionSample int64 = 5   // below this: INSUFFICIENT
    goodExecRate       float64 = 0.80
    goodToolRate       float64 = 0.70
    maxRetryRate       float64 = 0.30
)
```

### Zero Observations ≠ 0% Success

```go
if ps.ExecutionCount > 0 {  // Guard prevents division by zero
    // compute rate
}
// ExecutionCount == 0 → neutral (0.0 preference)
```

## 6. Tool Reliability Semantics

Tool telemetry is computed **independently** of execution count:

```
totalToolCalls = ToolCallSuccessCount + ToolCallFailureCount

if totalToolCalls > 0:
    if totalToolCalls < 5: INSUFFICIENT → neutral
    else: compute toolRate
        toolRate >= 0.70: positive bonus (up to +0.036×intensity)
        0 < toolRate < 0.70: negative penalty (down to -0.021×intensity)
```

### Attribution

- Tool calls are attributed to the **provider** that executed them
- In the agent loop, `resolved.ProviderModelID` is passed, so model-level attribution works
- A failed tool call is NOT attributed to whichever provider receives the final HTTP request — it's attributed to the provider/model that attempted the tool call

## 7. Retry Semantics

**Explicitly defined:**

| Concept | Representation | Notes |
|---------|---------------|-------|
| Primary attempt | `retryCount = 0` | Recorded as success/failure with 0 retries |
| Fallback success | `retryCount = i+1` | Number of fallbacks consumed |
| Fallback failure | `retryCount = i+1` | Same |
| Circuit breaker skip | Not recorded | Breaker rejection is pre-execution |
| Agent loop step | `retryCount = 0` | Each step is a fresh execution |

**Not collapsed:** Retry count is tracked separately from success/failure. High retry rates incur an additional penalty beyond the base execution success rate.

## 8. Unknown/Insufficient/Measured Semantics

| State | Condition | Routing Effect |
|-------|-----------|---------------|
| **UNKNOWN** | `ExecutionCount == 0` AND no model-level data | Neutral (0.0) |
| **INSUFFICIENT** | `0 < ExecutionCount < 5` | Neutral (0.0) |
| **MEASURED** | `ExecutionCount >= 5` | Applied (positive or negative) |

These states apply independently to:
- Provider-level execution counters
- Provider-level tool counters
- Model-level execution counters
- Model-level tool counters

## 9. RuntimeSnapshot Ownership

**Rule preserved:** `RuntimeSnapshot` remains the sole dynamic routing authority.

- Exactly one `RuntimeSnapshot` per pipeline execution (acquired in `DecisionPipeline.Execute()`)
- All scoring factors derive from this single snapshot
- No helper calls `RuntimeManager.Snapshot()` independently during the pipeline
- `MetricsStore` is retained for observability but does NOT influence routing

## 10. Planning Interaction

Planning mode uses `executionTelemetryPreference(snapshot, providerName, modelID, intensity=1.0)`:
- Same semantics as Agentic but with lower intensity (1.0 vs 1.5)
- Same provider→model fallback chain
- Same UNKNOWN/INSUFFICIENT/MEASURED state machine
- Hard requirements: Reasoning + ToolCalling (unchanged)

## 11. Agentic Interaction

Agentic mode uses `executionTelemetryPreference(snapshot, providerName, modelID, intensity=1.5)`:
- 1.5× stronger telemetry signal than Planning
- Same fallback chain (model-level → provider-level)
- Same state machine
- Hard requirements: Reasoning + ToolCalling + known-context (unchanged)
- Capability bonuses: ToolCalling=0.30, Reasoning=0.30, ContextCapacity=0.10 (unchanged)

## 12. Attribution Changes

### What Changed

1. **`ProviderStateSnapshot`** gained `ModelExecutions map[string]ModelExecutionState`
2. **`ProviderRuntime`** interface gained `RecordExecutionOutcomeModel()` and `RecordToolCallOutcomeModel()`
3. **`ExecutionToRuntimeAdapter`** methods gained `modelID` parameter
4. **Handler** passes `resolved.ProviderModelID` to all telemetry calls
5. **Agent loop** passes `resolved.ProviderModelID` to all telemetry calls
6. **`executionTelemetryPreference()`** prefers model-level, falls back to provider-level

### What Did NOT Change

- Provider-level counters continue to work exactly as before
- Empty modelID falls back to provider-level only (backward compatible)
- `RuntimeSnapshot` structure unchanged (only extended)
- DecisionPipeline architecture unchanged
- RouterEngine selection logic structure unchanged
- All existing mode behaviors preserved

## 22. Remaining Limitations

1. **No time-based expiration:** Telemetry counters are cumulative with no decay. Long-running deployments will accumulate stale history. This is intentional (simple, predictable) but may need addressing in a future stage.

2. **No per-request model identity in agent loop for tool retries:** If a tool call fails and is retried on a different model, the retry would be attributed to the original model. This is an edge case that does not affect the common path.

3. **Dashboard API does not yet expose model-level telemetry:** The `/api/models` and `/api/models/status` endpoints show provider-level state. Model-level data is available in `ProviderStateSnapshot.ModelExecutions` but not yet surfaced in dashboard responses. This is a documentation/API gap, not a correctness issue.

## 23. Recommended Next Stage

**P3.11: Telemetry Time-Bounded Decay**

Add configurable decay windows to execution telemetry so that:
- Old observations gradually lose weight
- New deployments aren't penalized by stale provider-wide history
- Model-level telemetry can have independent decay windows

This would make the telemetry truly self-correcting over time.
