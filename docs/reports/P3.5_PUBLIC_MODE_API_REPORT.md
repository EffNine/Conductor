# P3.5 Public Mode API Report

## 1. API Contract

A new `mode` field is added to `ChatCompletionRequest`:

```json
{
  "model": "auto",
  "mode": "reasoning",
  "messages": [...]
}
```

- Field: `Mode string` with JSON tag `json:"mode,omitempty"`
- Omitted when empty — preserves backward compatibility
- Validated at the handler layer before entering the pipeline
- Invalid values return `400 Bad Request` with the repository's existing `ErrorResponse` schema, identifying `param: "mode"` and `code: "invalid_request"`

Supported public values: `auto`, `coding`, `planning`, `agentic`, `reasoning`, `long_horizon`, `fast`, `vision`

Internal-only classifier `elite` is explicitly excluded from the public API.

## 2. Mode Resolution Precedence

1. **Explicit request.mode** — if non-empty, parsed via `router.ParseMode()` and used directly
2. **Canonical classifier** — if mode is omitted, `ClassifyRequest()` determines the mode from message content
3. **Default Auto profile** — the fallback when no signal exists

The explicit mode **overrides** classifier intent completely.

## 3. Explicit vs Inferred Mode

| Scenario | Behavior |
|----------|----------|
| `mode: "fast"` + reasoning-heavy text | Resolves to `ModeFast` (explicit wins) |
| No mode + "write a function" | Classifier infers `ModeCoding` |
| No mode + "hi" | Classifier infers `ModeFast` or `ModeDefault` |
| `mode: "auto"` | Explicitly uses `ModeDefault` profile |
| `mode: ""` (omitted) | Same as pre-P3.5: classifier-driven |

## 5. Invalid Mode Behavior

Invalid explicit mode values produce a **400 Bad Request**:

```json
{
  "error": {
    "message": "invalid mode \"reasonning\": supported values are auto, coding, reasoning, vision, fast, planning, agentic, long_horizon",
    "type": "invalid_request_error",
    "param": "mode",
    "code": "invalid_request"
  }
}
```

Invalid modes are **never** silently converted to Auto.

## 6. Explicit Model / Route Interaction

- Explicit model + mode: mode influences routing preferences within the candidates allowed by model/route resolution. The model is never silently replaced.
- Explicit route + mode: mode scores only the supplied candidates (primary + configured fallbacks). It does **not** expand the candidate set.
- One-candidate route: remains effectively pinned regardless of mode.

## 7. Vision Semantics

- **Explicit `mode=vision` without image content**: Vision is used as a routing preference/profile. No hard filter is applied.
- **Actual image/multimodal content present**: Existing hard vision filtering remains authoritative regardless of mode.
- Text mentioning "image" without actual image parts does **not** trigger hard vision rejection.

## 8. Streaming / Embeddings Semantics

- **Streaming**: Mode behavior is identical for `stream=true` and `stream=false`. The selected provider is the same for the same request state.
- **Embeddings**: The `mode` field is not part of `EmbeddingRequest`. If a client sends `mode` to `/v1/embeddings`, it is silently ignored during parsing — no chat routing semantics are applied. No validation error is produced (consistent with OpenAI API behavior for unknown fields).

## 9. Cache Audit

Cache keys now include the `mode` parameter:

```go
params := map[string]interface{}{
    ...
    "mode": req.Mode,
}
```

This ensures that two requests with identical model/messages but different modes produce distinct cache keys, preventing a cached response from one mode from being served for a request under a different mode.

## 10. DecisionTrace / Observability

The `DecisionTrace` records mode resolution metadata in the `IntentResolved` event:

```json
{
  "type": "intent.resolved",
  "timestamp": "...",
  "payload": {
    "resolved_mode": "reasoning",
    "mode_source": "explicit",
    "requested_mode": "reasoning"
  }
}
```

When mode is omitted, `mode_source` is `"classifier"` and `requested_mode` is `""`.
