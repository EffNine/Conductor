# P3.13 Capability Signal Quality & Mode Differentiation Audit Report

## 1. Executive Summary

P3.13 empirically audited the quality of capability signals and the semantic
differentiation of all eight public routing modes (`auto`, `coding`,
`reasoning`, `vision`, `fast`, `planning`, `agentic`, `long_horizon`). 53 new
tests across 12 test files measure, for every mode, the *primary signal*, the
*counter-signal crossover*, and the *score-contribution arithmetic* that
produces winners.

**Verdict: every mode is genuinely, measurably, and explainably
differentiated.** The composite score decomposes exactly into
`wH*health + wL*latency + wC*cost + wK*capability + 0.05*(mode bonuses)`
(identity verified to 1e-9 against real decisions). Hard filters (vision,
context, reasoning+tool_calling) are mode-correct. No engine redesign, no new
modes, and no new signals were required.

Findings classified: **1 bug fixed** (DecisionTrace carried no candidate
scores — the only justification-free gap in the explainability path),
**1 dead-code candidate** (`HealthFactor` is unused), **10 verified
contracts** locked by dedicated tests, and **2 documented behaviors** that are
correct but surprising (sub-100ms latency scores exceed 1.0 in trace output;
omitted-mode requests can fail on the inactive `elite` classification).

Verification: `go build ./...`, `go test ./...`, `go test -race ./...`, and
`go test -race -count=10 ./internal/router/...` all pass.

## 2. Scope & Method

Audited artifacts (all `internal/router`): `mode_profile.go`, `classifier.go`,
`scorer.go`, `selection.go`, `pipeline_stages.go`, `pipeline.go`,
`decision_context.go`, `decision_trace.go`, `capability.go`,
`context_estimation.go`, `runtime/types.go`, `policy/types.go`, plus
`internal/automode/classifier.go` and `internal/handler/handler.go`.

Method per phase: (a) derive the intended contract from the mode profile
definitions, (b) measure real behavior via controlled A/B experiments against
a calibration pipeline (stub providers with exact health/latency/cost/
capability/telemetry state), (c) decompose each winner into weighted factor
contributions to identify the winning signal, (d) classify findings as bug
(fix) / verified contract (lock) / intentional-but-surprising (document),
(e) re-run the full verification battery.

## 5. Weight Matrix & Normalization

Weights are normalized per decision (`effectiveWeights` →
`Normalize(RawWeights{...})`); the pipeline applies them as
per-decision overrides and never mutates the engine's global defaults
(`TestP313ModeWeightsArePerDecision` — engine weights byte-identical before
and after coding/fast/auto executions). `DefaultModeProfiles()` returns
defensive copies; mutating a returned profile cannot corrupt the table
(`TestP313ModeProfilesAreFreshCopies`).

## 11. Planning vs Agentic: Capability/Health Flip

`p3_13_planning_agentic_test.go` Cases A/B/C: planning (capability 45) prefers
the structured-capable degraded provider; agentic (health 55) prefers the
healthy provider; the flip direction reverses with state. Case C confirms
agentic's extra context hard filter (agentic rejects what planning accepts).

## 12. Planning vs Agentic: Telemetry Intensity 1.5×

Case D: identical poor-history vs excellent-history providers; both modes
choose the good-history provider, with margins **planning 0.060000 /
agentic 0.090000 — exactly 1.5×** (ratio asserted, not just direction). Case E:
proven-history beats stronger reasoning in both modes. The intensity factor
(1.0 vs 1.5) is the ONLY behavioral difference between the two modes' telemetry
handling.

## 13. Long-Horizon Context Sweep

`p3_13_longhorizon_context_test.go` sweeps request sizes through the
16384/32768/65536/128000/132096 boundaries (estimator
`4 + len/4 + 4096`): long_horizon inverts eligibility exactly at the
expected estimate crossing; other modes never apply the context hard filter.

## 14. Long-Horizon Explicit-Route Constraint

Explicit provider routes are constrained candidates, never expanded: a
route whose MaxContext < required is rejected with no fallback to other
providers; the same route without context pressure selects normally.
Unknown MaxContext (0) = no constraint, but also no bonus
(`TestP313LongHorizonUnknownContextNotPreferred`).

## 15. Fast Latency Crossover Analysis

`p3_13_fast_latency_test.go`. Latency gap 20ms→500ms = 0.06531 (raw).
Fast flips to the 25× slower provider when the health delta exceeds
`0.4*0.06531/0.55 = 0.0475`; auto flips at `0.25*0.06531/0.40 = 0.0408`.

- 20ms/health 0.95 vs 500ms/health 0.99 → fast picks 20ms (latency preference).
- 20ms/health 0.95 vs 500ms/health 1.00 → fast picks the 25× slower provider.
- 0.0455 health delta: auto flips, fast does not (fast is MORE
  latency-sensitive than auto, despite auto's smaller latency weight —
  because fast's health weight is also much higher).

**Contract: fast is "latency preference subject to health", NOT "lowest
latency at all costs" — verified on both sides of the crossover.**

## 16. Vision Semantics

`p3_13_vision_test.go`. Mode `vision` is a PROFILE, not a content
declaration:

- vision mode + text only → no hard reject; a non-vision provider can win.
- Text merely mentioning an image ("describe this image") → no reject
  (hints come from content parts, not words).
- Actual image content → non-vision candidates hard-rejected in **every**
  mode, including fast (the filter is request-driven, not mode-driven).
- Explicit route to non-vision provider + image → rejected, **no expansion**;
  same route without image → eligible.
- Unknown vision capability (no metadata) = **not-vision-capable** (no
  tri-state): rejected with image, eligible without.

## 17. Coding/Reasoning Composition

`p3_13_composition_test.go`. All three hints (tools + reasoning + structured)
compose: coding residual 0.025, reasoning residual 0.0175 (exact). Both modes
are capability-dominated: the capability-strong provider wins **even when
unhealthy** (coding 0.60 / reasoning 0.65 weight), yet the capability-weak
provider is never rejected (soft preference; matchScore floor 0.3). Contrast:
planning/agentic hard-reject the same weak provider.

## 18. Auto Mode Audit

`p3_13_auto_audit_test.go`.

- `automode.ClassifyTask` is a pure delegation to `router.ClassifyRequest` —
  there is **no competing classification path**.
- Explicit `Mode="auto"` → `ParseMode` → `ModeDefault` profile, trace
  `mode_source="explicit"`, `resolved_mode="default"` — the text is **not**
  re-classified.
- Omitted mode (`""`) → text classifier (`mode_source="classifier"`); coding
  keywords resolve to `coding` (capability weight 60) and change winners.
- Trace payload records `resolved_mode`/`mode_source`/`requested_mode` per
  decision (auditable).
- **Surprising but intended:** the classifier can resolve to the internal,
  inactive `elite` mode; an omitted-mode request with elite keywords
  ("implement a distributed microservice backend") fails the pipeline with
  "mode not yet supported". Explicit `auto` on the same text succeeds.

## 19. DecisionTrace Explainability

(decision.started, per-stage started + completed StageResults, intent.resolved

## 20. Weight Isolation & Concurrency

## 24. Bugs Found & Fixed

**One fix (category A, smallest justified schema gap):** `DecisionTrace`
recorded only the Winner and RejectionReasons — the per-candidate scores that
make a winner explainable were never populated
(`internal/router/decision_trace.go`, `pipeline.go`). Added
`CandidateScores []CandidateScore` to the trace and `SetCandidateScores`
builder method, populated in `Execute` alongside `SetWinner`/
`SetRejectionReasons`. Trace-to-decision identity verified by
`TestP313TraceCarriesCandidateScores`.

## 25. Intentional Behaviors Retained (no fix)

1. Fast's health-sensitivity (crossover analysis above) — correct design, not
   a defect; locked.
2. Context bonus presence-only — an engine redesign (magnitude-scaled bonus)
   is explicitly out of scope for P3.13.
3. Elite classification failure on omitted-mode requests — pre-existing
   classifier contract; explicit modes never hit it.
4. matchScore floors (0.3/0.5) for missing hints — soft-preference design.
5. Sub-100ms latency scores above 1.0 in trace output — harmless (composite
   clamps), but see §28.

## 28. Remaining Limitations

- Context estimation remains a chars-per-token heuristic; boundary tests pin
  the estimator contract, not tokenizer truth.
- `CandidateScore.LatencyScore` exposes the raw factor (can exceed 1.0 below
  100ms) while the composite uses the clamped value — trace consumers must
  clamp. (Category B: clamp the exposed value or document; deferred.)
- `HealthFactor` dead code remains (removal is a category-B cleanup).
- Context bonus magnitude-insensitivity is by design; revisit only if
  deployments show the 0.10 flat bonus misorders large-context providers.
- Omitted-mode elite classification failure could surprise API users (no
  config surface to remap "elite" today).

## 29. Recommendations / Next Stage

1. Remove `HealthFactor`/`NewHealthFactor` dead code (category B cleanup).
2. Clamp `LatencyScore` exposure to [0,1] in `CandidateScore` so trace
   consumers cannot misread sub-100ms values.
3. Consider remapping classifier `elite` output to `planning`/`agentic` for
   omitted-mode requests (or documenting the failure mode in API docs).
4. If long-horizon deployments show the flat context bonus misordering
   providers, evaluate a magnitude-scaled bonus (engine change, future
   stage).
5. No other changes recommended — the eight modes are correctly and
   measurably differentiated.
