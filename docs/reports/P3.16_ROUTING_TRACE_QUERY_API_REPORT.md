# P3.16 — Routing Trace Query API Report

Status: COMPLETE

Continues from P3.15 (routing trace persistence), which is complete and
verified. P3.16 exposes persisted routing decision traces through a read-only
dashboard API so operators and future dashboard tooling can inspect routing
decisions.

---

## 1. Executive Summary

Two new read-only HTTP endpoints were added on top of the P3.15 persistence
layer:

- `GET /api/routing/traces` — compact, filterable, paginated list of persisted
  routing decisions.
- `GET /api/routing/traces/:id` — the complete canonical `DecisionTrace` for
  one decision.

The endpoints reuse the **same** `SQLiteTraceStore` instance that backs trace
persistence (single database handle, no duplicate connections). The handlers
contain **no SQL** and depend only on the `router.TraceStore` interface. All
existing conventions (auth middleware, error envelope, query parsing,
snake_case JSON, 503 for unavailable subsystems) were followed; no new API
style was invented.

The API is strictly read-only: only GET routes exist, write verbs answer
404/405, and no request can mutate traces, routing state, runtime state,
telemetry, or cache behavior.

```
RuntimeSnapshot   = routing truth
DecisionTrace     = decision explanation
TraceStore        = persistence
Trace Query API   = read-only observability
```

## 2. Existing API Conventions

Audited handlers: `/api/routing`, `/api/runtime`, `/api/usage`,
`/api/usage/costs`, `/api/logs`, `/api/models`, `/api/models/status`,
`/api/metrics`, `/api/cache`, `/api/streams`, `/api/config`.

| Convention | Observed | Applied |
|---|---|---|
| Response envelope | Direct JSON payloads; `fiber.Map` objects; `{"models": [...]}` / typed structs | `{"data": [...], "pagination": {...}}` (spec-required shape) |
| Error envelope | `{"error": {"message", "type", "code"}}`; optional `"param"` | Same envelope, `"param"` on 400s |
| 400 style | `type: "invalid_request_error"`, `code: "invalid_request"` | Same |
| 404 style | `type: "invalid_request_error"` + specific `code` (e.g. `model_not_found`) | `code: "trace_not_found"` |
| 503 unavailable | `type: "server_error"` (HandleUsage/HandleRuntime/HandleForceProbe) | `code: "trace_store_unavailable"` |
| 500 DB failure | `type: "server_error"` | `code: "trace_query_failed"` |
| Auth | Global `middleware.Auth` (Bearer key, `/health` exempt) | Inherited automatically; no per-route auth added |
| Query parsing | `c.Query("...")`; `defaultLimit` helper; strict validation where safety matters (force-probe, config) | Dedicated strict parsers (`parseTraceLimit/Offset/Time`) |
| Pagination | `?limit=` on `/api/usage`, `/api/logs` | `limit` + `offset` with deterministic ordering |
| JSON naming | snake_case throughout | snake_case |
| Timestamps | RFC3339 UTC strings in dashboard payloads (e.g. `/api/runtime`) | RFC3339 UTC strings in summaries |

## 3. Endpoint Contract

### `GET /api/routing/traces`

Authenticated (Bearer API key, same as all `/api/*`). Lists persisted routing
decision traces, most recent first, with compact summaries.

Query parameters (all optional):

| Param | Semantics | Validation |
|---|---|---|
| `mode` | Filters **`resolved_mode`** (canonical mode on the trace, NOT the raw requested string). Normalized with `router.ParseMode` (case-insensitive, trimmed). `mode=auto` matches resolved `default` — resolved mode is always a canonical `Mode` value, never the raw input. | Unknown mode → 400 |
| `provider` | Exact match on `selected_provider` | — |
| `model` | Exact match on `selected_model` | — |
| `runtime_hash` | Exact match on `runtime_hash` (64-hex) | — |
| `outcome` | Exact match on `outcome`: `selected` \| `rejected` \| `failed` | — |
| `from` | RFC3339, inclusive lower bound on decision timestamp | Malformed → 400 |
| `to` | RFC3339, inclusive upper bound on decision timestamp | Malformed → 400 |
| `limit` | Page size. Default **50**, maximum **200** | `< 1`, `> 200`, non-integer → 400 |
| `offset` | Rows to skip. Default 0 | `< 0`, non-integer → 400 |

`from > to` → 400. Filtering is exact-match AND semantics — no SQL-like
syntax, no partial matching, no arbitrary expressions.

### `GET /api/routing/traces/:id`

Authenticated. Returns the complete persisted `DecisionTrace` (canonical JSON
payload as saved by P3.15) for the given decision ID. Unknown ID → **404** with
the error envelope (never 200 + null).

## 5. Single Trace Response

`GET /api/routing/traces/:id` returns the **canonical persisted `DecisionTrace`**
— the exact JSON payload written by the P3.15 store, deserialized from
`payload_json` (never reconstructed from summary columns). It carries the full
explanation contract: `decision_id`, `trace_schema_ver`, mode resolution
(`requested_mode`, `resolved_mode`, `mode_source`, `mode_description`,
`mode_traits`), `intent`, `capability_requirements`, `effective_weights`,
`mode_bonuses`, `runtime_hash`, `candidate_scores` (per-factor breakdown,
selected/rejected flags, rejection reasons), `winner`, `stage_results`
(per-stage status + duration), and `events` (timeline).

## 6. Query Parameters

All TraceFilter dimensions map 1:1 to query parameters (see section 3). The
handler builds a `router.TraceFilter` and delegates to `TraceStore.List`; the
store applies the filters in SQL (`WHERE` on indexed columns, parameterized —
no string concatenation).

## 7. Validation

Rejected with HTTP 400 + `"param"` + clear message:

- `limit < 1`, `limit > 200`, `limit` non-integer
- `offset < 0`, `offset` non-integer
- `from`/`to` not parseable as RFC3339
- `from > to`
- `mode` not a known public mode

Pathological values are rejected, never silently clamped or defaulted.

## 8. Pagination

`LIMIT/OFFSET` (no cursor pagination yet). Default `limit=50`, hard maximum
`200` at the API boundary (the store keeps its own 1000-row cap as a second
defense). Pages are deterministic because ordering is total (see section 9).

## 9. Ordering

```
ORDER BY timestamp DESC, decision_id DESC
```

`decision_id DESC` is a deterministic tiebreaker for colliding timestamps, so
page boundaries never shift between identical queries. Verified by
`TestTraceStoreListDeterministicOrdering` (same-timestamp rows ordered by ID)
and `TestRoutingTraceStablePagination` (repeated identical queries produce
identical pages).

## 10. Filtering Semantics

- `mode` filters **`resolved_mode`** (documented choice; requested mode stays
  visible on the summary as `requested_mode`, and the full trace preserves the
  raw requested string). Canonical normalization via `ParseMode`: `mode=Coding`
  and `mode= coding ` both match resolved `coding`. Unknown modes are rejected
  with 400 instead of silently returning an empty page.
- `provider`, `model`, `runtime_hash`, `outcome` are exact matches on the
  persisted column values.
- `from`/`to` are inclusive bounds on the decision `timestamp`, pushed into SQL
  so the timestamp indexes are used (no application-side full-table scan).

## 11. Database Query Strategy

The P3.15 indexes are used as-is (no schema changes in P3.16):

| Filter | Index |
|---|---|
| `timestamp` range / ordering | `idx_routing_traces_timestamp` |
| `resolved_mode` | `idx_routing_traces_timestamp_mode` |
| `selected_provider` | `idx_routing_traces_timestamp_provider` |
| `selected_model` | `idx_routing_traces_selected_model` |
| `runtime_hash` | `idx_routing_traces_runtime_hash` |

All filtering happens in SQL through GORM with parameterized queries; the
handler never sees SQL, tables, or the database type. No new indexes were
added — the existing set covers every filter dimension and the ordering.

## 12. Performance

Benchmarks on the real SQLite store (unchanged from P3.15; the API adds no
database work beyond the store calls):

| Operation | Latency |
|---|---|
| `Save` (full trace, unique ID) | ~102 µs |
| `List` (mode-filtered, limit 50) | ~43 µs |
| Canonical payload size | ~1.9 KB |

Live E2E observation: a decision persisted and became queryable within the
same second; list + filter responses complete in well under a millisecond on
the loopback smoke test. No over-optimization was performed; EXPLAIN QUERY
PLAN tests were deemed unnecessary because the query shapes are simple
point/range lookups on the existing indexes.

## 13. Authentication

Global `middleware.Auth` covers both endpoints automatically (registered via
`Handler.Register`, same as every other `/api/*` route): missing or invalid
Bearer key → 401. Verified live and in `TestRoutingTraceAuth`. `/health`
remains the only unauthenticated path.

## 14. Security

Audited at the API boundary:

- **Never exposes**: API keys, authorization headers, prompts, raw request
  bodies, provider credentials, internal filesystem paths.
- The full `DecisionTrace` payload is safe by the P3.14/P3.15 contract (no
  prompts/secrets by construction) — re-verified at the boundary with
  `TestRoutingTraceNoSecrets` (list + single responses scanned for key/secret
  markers) and `TestRoutingTraceNoPrompt`.
- Summary items contain only queryable dimensions — never the payload.
- All SQL is parameterized (store layer); the API layer performs no SQL.

## 15. Read-Only Guarantees

Only GET routes are registered. POST/PUT/DELETE/PATCH on either path answer
404/405 (verified live and in `TestRoutingTraceReadOnly`, which also confirms
the stored trace is unchanged after write attempts). There is no endpoint,
flag, or code path that can delete or modify a trace, retry a decision,
trigger routing, mutate `RuntimeSnapshot`, mutate telemetry, or change
provider state. No DELETE endpoint was added.

## 16. Handler Architecture

```
HTTP Handler (internal/handler/trace_query.go)
    |  router.TraceStore interface only
SQLiteTraceStore (internal/database/tracestore.go)
    |
routing_traces (SQLite)
```

The handler depends only on the `router.TraceStore` interface: no SQLite, no
SQL strings, no table names, no GORM. SQL remains exclusively in
`internal/database`. Routing code is untouched by the API.

## 17. Production Wiring

`cmd/conductor/main.go` now constructs the store once and shares it:

```go
traceStore = database.NewSQLiteTraceStore(db)
tracePersistence := database.NewTracePersistence(eventBus, traceStore, logger)
...
h.SetTraceStore(traceStore)   // same instance backs persistence + query API
```

One store, one database handle. When routing is disabled, `traceStore` stays
nil and the endpoints answer 503 — no crash at startup, no fallback database.

## 18. Persistence-Unavailable Behavior

When no store is wired (routing disabled, or future configurations without
persistence): both endpoints answer **503** with
`{"error": {"message": "Routing trace store not available", "type": "server_error", "code": "trace_store_unavailable"}}` —
the same convention as `/api/runtime` when the runtime manager is absent and
`/api/usage` when the database is nil. Startup is unaffected.

## 21. Bugs Found

1. **Test fixture mistake (model filter)**: the persisted `selected_model`
   column is derived from `Winner.ModelID` (the user-facing route model), not
   `Winner.ProviderModelID`. The initial fixture mutated the wrong field, so
   the filter matched nothing. Fixed the fixture; this also documents that
   `selected_model` is the user-facing model dimension.
2. **`TestRoutingTraceNoPrompt` false positive**: the fixture decision ID
   itself contained the substring "prompt", tripping the leak scan. Renamed
   the fixture ID. No actual leak existed.
3. **`TestRoutingTraceReadOnly` status expectation**: Fiber answers **405**
   (Method Not Allowed) for a registered path with an unregistered method,
   not 404. The test now accepts 404 or 405 — both prove no write route
   exists.

No production-code bugs were found. All findings were in the new tests
themselves; the P3.15 persistence layer was used exactly as designed.

## 22. Bugs Fixed

All three findings above were fixed in the test suite (no production code
changes were required). The API, store, and wiring shipped as written in the
first pass: build, vet, and the full suite passed on the first full run.

## 23. Intentional Behaviors

- `mode` filters `resolved_mode` only; `requested_mode` is preserved raw on
  the summary and in the full trace (no stored data is ever rewritten).
- `mode=auto` matches resolved `default` — resolved mode is canonical; the
  raw "auto" input is not a resolved value.
- `limit > 200` is **rejected** (400), not clamped; `limit < 1` likewise.
  Pathological values are never silently accepted.
- `count` in the pagination envelope is the number of rows in the current
  page, not a global total (no COUNT query; keeps list queries index-cheap).
- List summaries always serialize the same 14 fields — no conditional
  fields, stable JSON shape for dashboard tooling.
- `outcome` is exposed as a filter (maps directly to `TraceFilter.Outcome`)
  even though it was beyond the minimum parameter set.
- RFC3339 with second precision for summary timestamps (matches the
  dashboard convention of `/api/runtime`).

## 24. Future Dashboard Boundary

The API serves raw, paginated data only — no aggregates are computed
server-side. A future dashboard can derive, from the existing endpoint:

**Overview**
- routing volume → `GET /api/routing/traces` count per page over time
- mode distribution → group summaries by `resolved_mode`
- provider selection frequency → group by `selected_provider`
- failure rate → `outcome=failed` filtered queries

**Mode**
- mode → provider → filter by `mode`, group by `selected_provider`
- mode → latency → full traces (`stage_results` durations) per mode
- mode → score distributions → full traces (`candidate_scores`, `selected_score`)

**Provider**
- provider selection → filter by `provider`
- rejection frequency → full traces (`rejection_reasons`, `candidate_scores`)
- runtime hash correlation → filter by `runtime_hash`, compare snapshots

**Debug**
- decision ID → `GET /api/routing/traces/:id`
- full trace → candidate score breakdown, rejection reasons, stage results
- rejection reasons → full traces per decision

All of these can be built client-side today from the two endpoints; no
aggregation API was added (and none should be until a dashboard actually
needs it).

## 28. Final API Contract

```
GET /api/routing/traces
  Auth:        Bearer API key (global middleware; 401 without)
  Params:      mode | provider | model | runtime_hash | outcome
               from | to (RFC3339, inclusive) | limit (1..200, default 50)
               offset (>=0, default 0)
  Response:    200 {"data": [TraceSummaryResponse...],
                    "pagination": {"limit", "offset", "count"}}
  Ordering:    timestamp DESC, decision_id DESC
  Errors:      400 invalid param (envelope + "param")
               503 no store wired (trace_store_unavailable)
               500 store failure (trace_query_failed)

GET /api/routing/traces/:id
  Auth:        Bearer API key (401 without)
  Response:    200 canonical DecisionTrace JSON
  Errors:      404 trace_not_found (unknown id)
               503 no store wired (trace_store_unavailable)
               500 store failure (trace_query_failed)

Read-only:     POST/PUT/DELETE/PATCH -> 404/405 on both paths.
```

## 29. Recommended Next Stage

1. **P3.17 — Trace retention/cleanup policy** (the one write path worth
   adding): configurable TTL + size cap for `routing_traces` with a
   background sweeper, so unbounded trace growth is never possible. This is
   the natural successor because observability data, unlike routing data,
   has a finite useful life.
2. **P3.18 — Execution outcome correlation**: P3.15 left provider execution
   outcome out of the trace (execution happens after trace finalization).
   Correlating the trace's decision ID with request-level execution records
   (request log / usage) would make the trace API answer "was the chosen
   route actually successful?".
3. **P3.19 — Dashboard**: once P3.17/P3.18 exist, a read-only dashboard
   consuming sections 24's derivations would complete the observability
   story. Aggregate analytics endpoints should only be added when a
   dashboard actually needs them.
