# P3.7 Execution Capability Telemetry Foundation — Report

## 1. Current Telemetry Audit

### Existing Signals (Pre-P3.7)

| Signal | Location | Scope | Notes |
|--------|----------|-------|-------|
| `successCount` / `failureCount` / `totalRequests` | `runtime.ProviderRuntimeImpl` | Provider-level | Cumulative atomic counters; exposed via `GetStats()` and `Snapshot().ErrorRate` |
| `latencyMs` | `runtime.ProviderRuntimeImpl` | Provider-level | Single latest value (atomic); updated by `RecordLatency()` |
| Usage records | `usage.Tracker` → SQLite | Request-level, attributed to provider+model | Tokens, duration, status code, error message, stream flag |
| Step persistence | `agent.Step` struct + `AgentStore` | Task-level, per LLM call | Provider, model, latency, tokens, status, error |
| Tool call persistence | `agent.ToolCall` struct + `AgentStore` | Task-level, per tool invocation | Tool name, arguments, result, error, status |
| Task events | `agent.Event` + `AgentStore` | Task-level lifecycle | `task.step.started`, `task.step.completed`, `task.tool.started`, `task.tool.completed`, `task.completed`, `task.failed` |
| Health probe results | `health.ModelStatusStore` | Per-model reachability | State, latency, error rate, next probe time |
| State changes | `runtime.StateChange` | Provider-level | From→to state transitions with reason |
| EventBus events | `eventbus.EventBus` | In-process pub/sub | Provider lifecycle, decision pipeline, usage, task coordination |

### What Was Missing

- **No execution telemetry in `ProviderStateSnapshot`** — Could not answer "how often does provider X succeed at chat completion?" from the runtime view
- **No tool call telemetry at provider level** — Agent tracked tool calls per-task but never propagated to runtime
- **No retry counting in runtime** — Fallback retries were observable in logs but not persisted to runtime state
- **No execution-oriented EventBus events** — Only provider/decision/usage events existed
- **No adapter for execution outcomes** — The `UsageToRuntimeAdapter` only handled token/duration metrics

## 2. Existing Signals Reused

- **`ProviderRuntimeImpl` atomic counters pattern** — New execution/tool-call counters follow the same `atomic.Int64` pattern already used for `successCount`/`failureCount`/`totalRequests`
- **`RuntimeStore.Update()` pattern** — All telemetry updates go through `store.Update(name, func(r ProviderRuntime) error)` exactly like the usage adapter
- **`Adapter` pattern** — `ExecutionToRuntimeAdapter` mirrors the existing `UsageToRuntimeAdapter` and `BreakerToRuntimeAdapter`
- **EventBus publish pattern** — New events use the same `eventBus.Publish(ctx, Event{...})` pattern
- **Handler `recordModelResult()` hook** — Extended with `recordExecutionTelemetry()` alongside existing `recordModelResult()` and `trackUsage()`
- **Agent `persistStep()` / `recordUsage()` pattern** — New `recordExecutionStart()` / `recordExecutionFinish()` / `recordToolCallOutcome()` follow the same guard-pattern (`if a.runtimeMgr == nil { return }`)

## 4. Provider/Model Attribution

All telemetry is attributed at the **provider name** granularity:

- Handler records against `resolved.ProviderName` (e.g., `"openai"`, `"groq"`)
- Agent loop records against `resolved.ProviderName` from the step's route resolution
- Tool call outcomes are attributed to the provider that produced the tool-calling response

**Limitation**: Provider-level rather than provider+model level. This is intentional for P3.7 — the existing `ProviderRuntimeImpl` is keyed by provider name, and model-level attribution would require a two-level store. The cumulative counters are coarse but sufficient for future routing decisions that compare provider reliability.

---

## 5. Runtime Ownership

- **Single source of truth**: `RuntimeSnapshot` (via `runtime.Manager.Snapshot()`) remains the authoritative dynamic view
- **No second telemetry store**: All execution signals flow through `RuntimeStore.Update()` into `ProviderRuntimeImpl`
- **No MetricsStore for routing**: `MetricsStore` in `router/scorer.go` is unchanged and not read by routing
- **No direct RouterEngine inspection**: RouterEngine continues to score exclusively from `RuntimeSnapshot`
- **Async-safe updates**: All telemetry updates go through `RuntimeStore.Update()` which acquires the store lock, then calls the provider's atomic methods — no races

## 7. Unknown/Zero/Sample Semantics

| Condition | Counter Values | Interpretation |
|-----------|---------------|----------------|
| No executions ever | All = 0 | **Unknown** — no data, cannot infer reliability |
| 1 success, 0 failures | Success=1, Failure=0 | Successful (but insufficient sample) |
| 0 successes, 1 failure | Success=0, Failure=1 | Failed (but insufficient sample) |
| Many executions, high success rate | Success>>Failure | Confidently reliable |

**Key invariant**: Zero counts remain distinguishable from "no data" because the counters start at 0 and only increment on actual events. Consumers can check `ExecutionCount == 0` to detect "no data" vs. `ExecutionCount > 0 && ExecutionSuccessCount == 0` for "all failed".

**No rolling rates are computed in the snapshot.** P3.7 stores raw cumulative counters. Future P3.8+ routing can derive rates with minimum sample thresholds.

## 8. Tool-Call Observability Limitations

### What Conductor Can Observe

- **Agent-mode tool calls**: The agent loop (`internal/agent/loop.go`) executes tools via `tool.Registry` and records success/failure per call. These are now propagated to runtime telemetry.
- **Chat completion tool-call intent**: The handler observes whether the provider returned tool calls in the response, but **does not** track individual tool call outcomes for non-agent (direct chat) requests — those tool calls are executed by the client, not Conductor.

### What Conductor Cannot Observe

- **Direct chat requests with tool calls**: When a client sends a request with `tools` but no agent loop runs (the standard OpenAI-compatible path), Conductor forwards the request and response but does not execute the tools. Therefore, `ToolCallSuccessCount` and `ToolCallFailureCount` only reflect agent-executed tool calls.
- **Tool call count per request**: There is no `ToolCallCount` field — only success/failure aggregates.

This limitation is documented and intentional. The telemetry measures what Conductor actually controls.

## 9. Multi-Step Definition

"Step" is defined by the **agent loop iteration** in `internal/agent/loop.go`:

- Each `ctx2.Step++` represents one LLM call attempt
- A step succeeds if the provider returns a non-empty choice without tool calls (final response)
- A step is a "tool step" if the choice contains `ToolCalls` — the step continues to the next iteration after tool execution
- A step fails if the provider call errors or returns an empty choice

**Handler-level requests** (non-agent) do not have "steps" — they are single-shot. `ExecutionCount` increments once per handler request regardless of tool-call depth.

**Agent-level requests** increment `ExecutionCount` once per step (per LLM call), not per task. This means `ExecutionCount` ≈ total LLM calls across all tasks.

## 10. EventBus Changes

Added 3 event types to `internal/eventbus/eventbus.go`:

```go
ExecutionStarted EventType = "execution.started"
ExecutionFinished EventType = "execution.finished"
ToolCallCompleted  EventType = "tool_call.completed"
```

- `ExecutionStarted` is published by `ExecutionToRuntimeAdapter.OnExecutionStarted()` (currently not called from handler — the adapter's `OnExecutionFinished` is the primary telemetry point)
- `ExecutionFinished` payload: `map[string]any{"provider": ..., "success": ..., "retry_count": ...}`
- `ToolCallCompleted` payload: `map[string]any{"provider": ..., "success": ...}`

These events support observability (structured logging, external monitoring) without duplicating the runtime store as a data source.

## 12. Handler/Task/Agent Instrumentation

### Handler (`internal/handler/handler.go`)

Added `executionAdapter *runtimeadapter.ExecutionToRuntimeAdapter` field and `SetExecutionAdapter()` setter.

Instrumented at 6 points in `handleNonStreaming()`:
1. Primary success → `recordExecutionTelemetry(provider, true, 0)`
2. Primary failure → `recordExecutionTelemetry(provider, false, 0)`
3. Fallback success (index i) → `recordExecutionTelemetry(provider, true, i+1)`
4. Fallback failure (index i) → `recordExecutionTelemetry(provider, false, i+1)`
5. All-fallbacks-failed → final error recorded via primary provider's failure path

Instrumented at 6 analogous points in `handleStreaming()`.

### Agent Loop (`internal/agent/loop.go`)

Added `runtimeMgr runtime.Manager` field and `WithRuntimeManager()` setter.

Instrumented at 4 points:
1. After provider resolution in each step → `recordExecutionStart(providerName)`
2. On provider call error → `recordExecutionFinish(providerName, false)`
3. On successful provider response → `recordExecutionFinish(providerName, true)`
4. On each tool call outcome (success and failure paths) → `recordToolCallOutcome(providerName, success)`

### No Behavior Changes

All instrumentation calls are no-op when the adapter/manager is nil. No control flow, retry logic, fallback ordering, or response generation is altered.

## 19. What P3.8 Planning Can Consume

P3.8 (Planning mode activation) can read from `RuntimeSnapshot`:

- `ExecutionSuccessCount` / `ExecutionFailureCount` → compute provider reliability for planning-intensive tasks
- `RetryCount` → identify providers that frequently need fallbacks (unreliable for complex planning)
- `ExecutionCount` → minimum sample gate (skip providers with 0 executions)
- `ToolCallSuccessCount` / `ToolCallFailureCount` → assess tool-use reliability for plan execution
- New EventBus events (`ExecutionFinished`, `ToolCallCompleted`) → real-time observability

Planning routing can then decide: "Should this provider be trusted with multi-step plan execution?"

---

## 20. What P3.9 Agentic Can Consume

P3.9 (Agentic mode activation) can additionally consume:

- All P3.8 signals above
- Agent-loop step persistence (`task.step.completed` events with latency) → per-step duration distribution
- Tool call outcomes per-provider → which providers reliably execute which tools
- `RetryCount` distribution → agents need providers that don't constantly fail mid-execution
- Existing `Step` and `ToolCall` DB records → historical per-task execution depth and tool success patterns

Agentic routing can then decide: "Which provider has the best tool-execution reliability for autonomous agents?"

**P3.7 is complete.**

- Real execution telemetry exists for observable outcomes (provider chat completion success/failure, agent tool call outcomes)
- Telemetry is attributable to provider where the architecture permits
- Unknown telemetry (zero counts) is distinct from measured failure
- `RuntimeSnapshot` remains the authoritative dynamic view
- Updates are concurrency-safe (all atomic, race detector clean)
- Existing routing behavior is unchanged (3 regression tests verify this)
- Planning remains inactive (`ParseMode("planning")` still returns unsupported)
- Agentic remains inactive (`ParseMode("agentic")` still returns unsupported)
- Long Horizon remains fully functional
- All tests pass, race detector passes, build passes
- Clear consumption path for P3.8 (Planning) and P3.9 (Agentic)
