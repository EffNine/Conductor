# P3.9 Agentic Mode Activation — Report

## 1. P3.7 Telemetry Audit

### Available Signals

| Field | Scope | Semantics |
|-------|-------|-----------|
| `ExecutionCount` | Provider-name | Cumulative LLM call attempts (success + failure) |
| `ExecutionSuccessCount` | Provider-name | Successful chat completion responses |
| `ExecutionFailureCount` | Provider-name | Failed chat completion responses |
| `ToolCallSuccessCount` | Provider-name | Successful tool executions (agent loop only) |
| `ToolCallFailureCount` | Provider-name | Failed tool executions (agent loop only) |
| `RetryCount` | Provider-name | Total fallback retries across all executions |

### What "Step" Means

Per P3.7 documentation and `internal/agent/loop.go`:
- A "step" is one iteration of the agent loop (one LLM call)
- `ExecutionCount` = total LLM calls across ALL tasks for a provider
- There is NO per-task step count in the runtime snapshot
- There is NO multi-step execution telemetry that distinguishes single-step from multi-step at the provider level

### Attribution

All telemetry is at **provider-name** granularity. No provider+model sub-counters exist. This is a P3.7 design limitation acknowledged but not changed in P3.9.

### Key Limitation

**No reliable multi-step execution depth signal exists.** The existing `ExecutionCount` represents total LLM calls, not sustained multi-step task completion. Therefore:
- We CANNOT derive "multi-step success rate" from available telemetry
- We CANNOT derive "successful execution depth" per task
- We document this as a limitation and use the best available signals: execution reliability, tool reliability, and retry intensity

## 2. Definition of Agentic Execution

Agentic mode represents:
> "Select a model/provider capable of sustained multi-step reasoning and tool execution, with strong observed execution reliability and tolerance for deeper execution horizons."

Agentic is meaningfully stricter and more execution-oriented than Planning:
- Same hard capability requirements (Reasoning + ToolCalling)
- Stronger execution telemetry preference (intensity 1.5× vs 1.0×)
- Context requirement enforcement (reuses Long Horizon mechanism)
- Higher health weight (55 vs 40) reflecting reliability priority

## 3. Multi-Step Semantics

### What We CAN Measure

- **Execution success rate**: `ExecutionSuccessCount / (ExecutionSuccessCount + ExecutionFailureCount)`
- **Tool-call success rate**: `ToolCallSuccessCount / (ToolCallSuccessCount + ToolCallFailureCount)`
- **Retry intensity**: `RetryCount / ExecutionCount`

### What We CANNOT Safely Measure

- **Per-task step count**: Not available in RuntimeSnapshot
- **Multi-step vs single-step distinction**: Not tracked at provider level
- **Sustained execution depth**: No per-task completion telemetry in runtime

### Decision

We do NOT fabricate a synthetic "multi-step score." We use the available execution reliability signals as proxies for "sustained execution capability." This is documented as a limitation.

## 4. Hard Requirements

| Requirement | Type | Enforcement |
|-------------|------|-------------|
| Reasoning capability | Hard | Reject if `!caps.Reasoning` |
| ToolCalling capability | Hard | Reject if `!caps.ToolCalling` |
| Context adequacy | Hard | Reuses Long Horizon filter when `ModeAgentic` is active |
| Circuit breaker | Hard | Existing breaker rejection |

## 5. Soft Preferences

| Preference | Agentic Intensity | Planning Intensity | Notes |
|------------|-------------------|-------------------|-------|
| Execution reliability | 1.5× | 1.0× | Stronger weighting for Agentic |
| Tool-call reliability | 1.5× | 1.0× | Stronger weighting for Agentic |
| Retry penalty | 1.5× | 1.0× | Stronger penalty for Agentic |
| Health | 55% weight | 40% weight | Higher base weight |
| Capability | 30% weight | 45% weight | Lower base weight (capabilities already hard-filtered) |
| Latency | 10% weight | 10% weight | Same |
| Cost | 5% weight | 5% weight | Same |

## 6. Execution Reliability Calculation

```go
execRate := float64(ps.ExecutionSuccessCount) / float64(ps.ExecutionSuccessCount+ps.ExecutionFailureCount)
```

Thresholds:
- `minExecutionSample = 5`
- `goodExecRate = 0.80`
- Bonus: `+0.05 * intensity * (execRate - 0.80 + 0.20)` → max +0.09 (at intensity=1.5)
- Penalty: `-0.05 * intensity * (0.80 - execRate)` → min -0.06 (at intensity=1.5)

Cold-start semantics:
- `ExecutionCount == 0`: UNKNOWN → neutral (0.0)
- `0 < ExecutionCount < 5`: INSUFFICIENT → neutral (0.0)
- `ExecutionCount >= 5`, `execRate >= 0.80`: MEASURED GOOD → positive bonus
- `ExecutionCount >= 5`, `0 < execRate < 0.80`: MEASURED POOR → negative penalty
- `execRate == 0`: MEASURED POOR → maximum negative penalty

## 7. Tool-Call Reliability Calculation

```go
toolRate := float64(ps.ToolCallSuccessCount) / float64(ps.ToolCallSuccessCount+ps.ToolCallFailureCount)
```

Thresholds:
- `minExecutionSample = 5` (same gate as execution)
- `goodToolRate = 0.70`
- Bonus: `+0.03 * intensity * (toolRate - 0.70 + 0.20)` → max +0.054 (at intensity=1.5)
- Penalty: `-0.03 * intensity * (0.70 - toolRate)` → min -0.032 (at intensity=1.5)

Independent of execution count: tool-call telemetry is computed regardless of whether execution count meets the sample threshold.

## 8. Retry Semantics

```go
retryRate := float64(ps.RetryCount) / float64(ps.ExecutionCount)
```

Only applied when `ExecutionCount >= minExecutionSample`.
- `maxRetryRate = 0.30`
- Penalty: `-0.03 * intensity * (retryRate - 0.30) / 0.70` → max -0.045 (at intensity=1.5)

## 9. Execution-Depth Semantics

**Limitation documented**: Reliable multi-step execution depth telemetry is NOT available at the provider level in RuntimeSnapshot.

The existing `ExecutionCount` represents total LLM calls across all tasks, not per-task step counts. Therefore:
- We do NOT invent a synthetic "execution depth" score
- We do NOT fabricate a "multi-step success rate"
- We use execution reliability (`execRate`) as the best available proxy for "sustained execution capability"
- A provider with high execution success rate is preferred as it indicates reliability for multi-step workloads

If future P3.10+ adds per-task step count telemetry to RuntimeSnapshot, Agentic can be enhanced to use a normalized successful-step-depth signal.

## 10. Cold-Start / Unknown Semantics

| Condition | Counter Values | Interpretation | Score Contribution |
|-----------|---------------|----------------|-------------------|
| No data | `ExecutionCount == 0` | UNKNOWN | 0.0 (neutral) |
| Insufficient | `0 < ExecutionCount < 5` | INSUFFICIENT | 0.0 (neutral) |
| Measured good | `ExecutionCount >= 5`, `execRate >= 0.80` | MEASURED GOOD | Positive bonus |
| Measured poor | `ExecutionCount >= 5`, `0 < execRate < 0.80` | MEASURED POOR | Negative penalty |

**Key invariant**: Zero counts are distinguishable from measured failure. Unknown telemetry remains neutral — never a hard rejection.

## 11. Model/Provider Attribution

Per P3.7 design, all telemetry is attributed at the **provider name** granularity:
- `ExecutionCount`, `ExecutionSuccessCount`, etc. are keyed by provider name in `RuntimeSnapshot`
- No provider+model sub-counters exist
- The `executionTelemetryPreference` method reads from `snapshot.Providers[providerName]`

**Limitation acknowledged**: Provider A's execution history is attributed to all models on that provider. For Agentic routing, this is acceptable because:
1. Agentic requires reasoning + tool-calling capabilities which are provider-level advertisements
2. The preference is soft (bounded ±0.15 at intensity=1.5) and only influences selection among equally-qualified candidates
3. Model-specific capability filtering (hard filter) is still enforced independently

## 12. Context Interaction

Agentic composes with Long Horizon context enforcement:
1. The `CapabilityStage` sets `ContextRequirement` for both `ModeLongHorizon` and `ModeAgentic`
2. The selection loops apply a hard context filter for both modes
3. Known insufficient MaxContext → HARD REJECT
4. Unknown MaxContext (`MaxContext == 0`) → remain eligible (backward compatibility)

This is verified by `TestAgenticContextRequirement`.

## 14. Scoring Changes

The scoring architecture extends the existing framework without replacing it:

```
CompositeScore = existing weighted score
               + mode capability bonuses (Reasoning +0.30, ToolCalling +0.30, ContextCapacity +0.10)
               + execution telemetry preference (±0.15 at intensity=1.5)
               + tool telemetry preference (±0.054 at intensity=1.5)
               - retry penalty (up to -0.045 at intensity=1.5)
```

The mode-specific weights (Health=55, Latency=10, Cost=5, Capability=30) are normalized per-decision and do not mutate global RouterEngine weights.

### Constants

```go
const (
    minExecutionSample int64 = 5
    goodExecRate       float64 = 0.80
    goodToolRate       float64 = 0.70
    maxRetryRate       float64 = 0.30
)
```

Same constants as Planning; Agentic uses `intensity=1.5` to amplify the effect.

## 15. RuntimeSnapshot Flow

1. `DecisionPipeline.Execute()` acquires ONE snapshot via `runtimeMgr.Snapshot(ctx)`
2. Snapshot is stored in `DecisionContext.runtimeSnap`
3. `SelectionStage` passes the same snapshot to `RouterEngine.selectBestProviderWithMode()`
4. `scoreCandidateWithMode()` derives all operational state from the snapshot
5. `executionTelemetryPreference()` reads execution counters from the snapshot with Agentic intensity

**Invariant preserved**: Exactly one `RuntimeSnapshot` per pipeline execution.

## 16. Explicit Route/Fallback Behavior

### Explicit model/route + mode=agentic

- Candidates are constrained to the explicitly supplied set
- Agentic hard filter rejects unqualified candidates within that set
- If the single candidate lacks Reasoning or ToolCalling: **rejected**, not silently expanded
- If a fallback in the candidate set satisfies Agentic: **fallback wins**

### Auto mode + mode=agentic

- All registered providers are considered
- Agentic hard filter rejects non-qualifying providers
- Remaining providers are scored with stronger telemetry preferences

### Single candidate pinned

- If exactly one candidate satisfies Agentic requirements: it remains effectively pinned
- If exactly one candidate does NOT satisfy Agentic requirements: returns empty selection

These semantics are verified by:
- `TestAgenticExplicitRouteConstraint`
- `TestAgenticFallbackCanWin`
- `TestAgenticSingleQualifiedCandidatePinned`
- `TestAgenticSingleUnqualifiedCandidateRejected`

## 23. Remaining Limitations

1. **Provider-only telemetry attribution**: Execution history is at provider-name granularity, not provider+model. This is a P3.7 design limitation, not a P3.9 regression.

2. **No per-task step count in runtime**: `ExecutionCount` is cumulative across all tasks. Per-task step counts exist only in the task store (SQLite), not in RuntimeSnapshot.

3. **No multi-step execution depth signal**: Cannot distinguish "sustained multi-step success" from "single-shot success." Execution reliability is used as the best available proxy.

4. **Cumulative (not rolling) counters**: Telemetry accumulates indefinitely. For production use, a rolling window or TTL-based decay would be preferable. Out of scope for P3.9.

5. **No synthetic confidence score**: Per instructions, no "agentic-quality score" was invented. Only observable signals from P3.7 telemetry are used.
