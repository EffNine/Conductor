# P3.12 Routing Edge-Case Contract Hardening Report

## 1. Executive Summary

P3.12 audited the six edge-case findings carried over from P3.11 and hardened
the routing contracts that were ambiguous, silently lossy, or blocking. Four
genuine correctness gaps were found and fixed:

1. **Cache key omitted provider identity** — requests that can legitimately
   execute against different providers collided in the response cache
   (`internal/handler/handler.go` `buildCacheKey`). Fixed: provider name is
   now a key dimension.
2. **Present-but-insufficient model telemetry blocked provider fallback** —
   a model telemetry entry with fewer than 5 samples silently masked
   measured-good provider-level telemetry in Planning/Agentic scoring
   (`internal/router/selection.go` `executionTelemetryPreference`). Fixed:
   per-signal independent resolution with UNKNOWN/INSUFFICIENT/MEASURED
   precedence.
3. **Mode API was case-sensitive and whitespace-sensitive** — "Coding" or
   " planning " were rejected as invalid (`internal/router/classifier.go`
   `ParseMode`). Fixed: canonical `NormalizeMode` (lowercase + trim) as the
   single source of truth; raw input preserved for audit.
4. **Mode-constant documentation was stale** — Planning/Agentic/LongHorizon
   were commented "recognized but not implemented" although they are fully
   active since P3.8/P3.9.

Planning vs Long Horizon, unhealthy vs circuit-open, and context boundary
semantics were audited and **verified correct**; they are now locked by
dedicated regression tests. A latent test-harness trap (model capability
overrides wiping boolean capabilities) was fixed in the shared calib helper.

Verification: `go build ./...`, `go test ./...`, `go test -race ./...`, and
`go test -race -count=10 ./internal/router/...` all pass.

## 2. Scope & Method

Audited artifacts (all in `internal/router` and `internal/handler`):

Method: for each P3.11 finding, (a) re-derive the intended contract from the

dedicated tests plus end-to-end integration tests, (e) run the full
verification battery.

## 3. Cache Identity Contract

**Contract (now documented in `handler.go` `buildCacheKey`):**

- **Model dimension** = the RESOLVED provider model ID (`ProviderModelID`).
  Two aliases resolving to the same provider/model share a key; different
  resolved models never collide.
- **Provider dimension** = the resolved provider name (`ProviderName`).
  Two requests that can legitimately execute against different providers must
  never share a cache entry, because provider responses can differ and
  provider availability differs.
- **Mode dimension** = the CANONICAL mode (`NormalizeMode`). Equivalent
  spellings share a key; omitted mode (empty) stays distinct from explicit
  "auto" (locked P3.11 rule).
- **Request dimensions** = routing-relevant parameters: tools, tool_choice,
  reasoning controls, response_format, sampling params, multimodal content,
  user, seed.

## 4. Cache Collision Audit (Finding #1 — BUG FIXED)

**Old behavior:** `buildCacheKey(req, resolved)` keyed on
`resolved.ProviderModelID` + messages + params; the provider name was absent.
Two providers serving the same model slug (e.g. `gpt-4o` on `openai` vs
`azure`, or `provider-prefixed` IDs `openai/gpt-4o` vs `azure/gpt-4o`)
produced byte-identical cache keys. A cached response produced by provider A
could be served for a request routed to provider B, and — more subtly — a
provider that becomes unhealthy could still "answer" from cache with stale
content that B would never have produced.

**Fix:** `params["provider"] = resolved.ProviderName` in
`internal/handler/handler.go:1666` (plus canonical mode, see §12). Every
route resolution that changes provider changes the key; every resolution that
preserves provider+model+mode still hits the cache.

## 6. Telemetry Precedence Contract

**Contract (now documented in `selection.go`):** each telemetry signal
(execution success, tool-call success, retry rate) is resolved
**independently**:

- **Model MEASURED** (count ≥ `minExecutionSample` = 5): the model-level
  signal is used. A measured-poor model signal NEVER falls back to provider
  data.
- **Model UNKNOWN** (no entry) or **INSUFFICIENT** (count < 5): the
  provider-level signal is used if it is MEASURED.
- **Provider UNKNOWN/INSUFFICIENT**: the signal is neutral (0.0).

A measured model signal in one dimension does not block provider data in
another dimension (e.g. a model with 10 executions but no tool-call history
still uses provider tool-call data).

## 7. UNKNOWN / INSUFFICIENT / MEASURED Definitions

| Signal state | Condition | Contribution |
|---|---|---|
| UNKNOWN | no entry at the level, or count == 0 | neutral (0.0) |
| INSUFFICIENT | 0 < count < 5 (`minExecutionSample`) | neutral at that level; fallback to the other level if it is MEASURED |
| MEASURED | count ≥ 5 | rate-based bonus/penalty |

Rate semantics of a MEASURED signal (locked P3.11 formulas, unchanged):
good rate ≥ threshold → positive bonus; 0 < rate < threshold → negative
penalty; rate == 0 (all failures) → neutral by documented P3.11 design
(see §19); retry rate > 0.30 → penalty.

## 8. Telemetry Precedence Fix (Finding #2 — BUG FIXED)

**Old behavior:** a single binary switch — if a model entry existed at all
(`es != nil`, even with 0–4 samples), ALL three signals came from the model
level; the provider level was entirely masked.

**Bug:** a provider with great provider history but a fresh/partial model
entry (e.g. 2 samples after a model deployment) scored neutral — losing to
worse providers — precisely when the fresh model signal was least reliable.

**Fix:** `executionTelemetryPreference` rewritten around
`resolveTelemetrySignal` (per-signal precedence) with identical rate formulas
and bounds (`[-0.10*intensity, +0.10*intensity]`; agentic intensity 1.5).
The updated P3.11 test `TestP311PartialModelTelemetryFallsBackToProvider`
locks the new contract: 2 model samples + 10/10 provider samples → provider
telemetry applies.

## 10. Planning vs Long Horizon Semantics (Finding #3 — VERIFIED)

Both modes share identical normalized weights (health 40 / latency 10 /
cost 5 / capability 45) but differ in exactly three deliberate ways
(`mode_profile.go`):

| Aspect | Planning | Long Horizon |
|---|---|---|
| Telemetry preference | yes (intensity 1.0) | no |
| Context hard filter | no | yes |
| Reasoning+ToolCalling hard filter | yes | no |
| Capability bonus | ToolCalling 0.20 + Reasoning 0.25 | ContextCapacity 0.10 |

**Verified differentiation scenarios** (`p3_12_planning_longhorizon_test.go`):
aaa (32k context, cost 0.0005, 10/10 model telemetry) vs zzz (128k context,
cost 0.0001, 3/10 model telemetry):

- Planning prefers aaa (telemetry +0.02 beats zzz's cost +0.02) — execution
  reliability matters.
- Long Horizon prefers zzz — telemetry ignored, cost decides.
- Oversized request (max_tokens 33000 → required 33005): Long Horizon
  hard-rejects aaa (`insufficient context (32768 < 33005)`); Planning does
  not enforce a context budget at all.
- Both Planning and Agentic hard-reject providers lacking reasoning or
  tool-calling, regardless of other advantages.

No weight or formula changes were needed; the semantics were already
differentiated and are now locked.

## 11. Unhealthy vs Circuit-Open Semantics (Finding #4 — VERIFIED)

| Condition | Health score | Eligibility |
|---|---|---|
| StateUnhealthy / StateRecovering | 0.1 (soft) | eligible — can be selected |
| Open circuit breaker | n/a (hard reject, `circuit breaker open`) | never selectable in any mode |

**Locked tests** (`p3_12_health_semantics_test.go`), all 8 public modes:

- `TestP312UnhealthySoleCandidateEligibleAcrossModes` — unhealthy sole
  candidate is selected with health score ≤ 0.15.
- `TestP312UnhealthyLosesToHealthyBySoftMargin` — unhealthy is soft: healthy
  competitor wins; unhealthy is never marked rejected.
- `TestP312CircuitOpenHardRejectsAcrossModes` — open breaker → no selection,
  rejection reason `circuit breaker open`.
- `TestP312CircuitOpenBeatsEverySoftAdvantage` — open-breaker candidate loses
  even when dominating latency/cost/capability.

## 12. Mode Normalization Contract (Finding #5 — FIXED)

**Old behavior (locked by P3.11 tests):** `ParseMode` was exact-match;
`"AUTO"`, `"Vision"`, `" planning"` were rejected as invalid.

**Assessment:** case/whitespace sensitivity is not a routing-semantics
decision — it is API friction with zero correctness value. Normalization is a
strict superset of previously valid inputs (all previously valid modes still
parse identically), so the change is backward compatible.

**Fix** (`internal/router/classifier.go`):

- `NormalizeMode(s)` = lowercase + trim; **empty stays empty** — the omitted
  mode is a distinct API input from explicit `"auto"` and is never conflated
  with it. Documented as the single canonicalization point.
- `ParseMode` normalizes internally, so handler validation
  (`handler.go:223`), `IntentStage` (`pipeline_stages.go:40`), and the cache
  key all agree.
- `buildCacheKey` uses `NormalizeMode(req.Mode)`; the raw user string is
  preserved in `DecisionContext.RequestedMode` for auditability.
- Truly unknown strings (e.g. `"bogus"`, `"elite"`, `" DEFAULT "`) still
  return `invalid mode` and the pipeline still rejects them with 400.

**Locked tests:** `p3_12_mode_normalization_test.go` (NormalizeMode contract,
ParseMode acceptance, unknown rejection, pipeline rejection, raw
requested_mode preservation) and the rewritten P3.11 tests
`TestP312UppercaseModeNormalized`, `TestP312WhitespaceModeNormalized`,
`TestP312PipelineAcceptsNormalizedMode` (replacing the old case-sensitivity
tests).

## 13. Context Boundary Contract (Finding #6 — VERIFIED)

The Long Horizon / Agentic hard filter (`selection.go`:
`caps.MaxContext > 0 && caps.MaxContext < requiredContext → reject`) is
already **boundary-inclusive and proportional**:

- required == MaxContext → **eligible**; required == MaxContext+1 → rejected.
- Unknown MaxContext (0) → always eligible.
- Input estimate is conservative and proportional: 4 structural tokens per
  message, content/4 chars, +5 per image part, 8+def per tool, reasoning
  controls; output budget = `req.MaxTokens` if positive else
  `DefaultMaxTokens` (4096).

**Locked tests** (`p3_12_context_boundary_test.go`): exact-boundary and
one-above rejection, unknown-context eligibility, default output budget
(4100/4099), multimodal contribution (8201/8200), tool contribution
(8205/8204), and filter-only-in-long-horizon/agentic across all other modes
(max_tokens 1,000,000 on a 1024-context provider).

## 14. RuntimeSnapshot Invariants

Verified unchanged (P3.10/P3.11 design, no code changes):

- One coherent snapshot per decision; all scoring inputs derive from it.
- Model telemetry keyed by resolved `ProviderModelID`; provider counters
  always accumulate in parallel (store.go `RecordExecutionOutcomeModel`).
- Snapshot exposure: `runtime/types.go` `ProviderStateSnapshot.ModelExecutions`
  — nil when no model entries exist (map preserved as nil, not empty, in
  `copyModelExecutions`).
- No new telemetry dimensions were added; counters are monotonic.

## 15. Determinism Contract

- Tie-break is deterministic: provider-name sorted order for auto-mode
  discovery; route order for pre-resolved routes; `scoreEpsilon = 1e-9`
  guards float noise (locked P3.11 invariants still pass).
- The regression matrix (below) relies on this: identical-score pairs resolve
  to the alphabetically first provider, verified across 32 (mode × telemetry)
  combinations.
- Adding a worse candidate cannot change the winner
  (`TestP311AddingWorseCandidateCannotChangeWinner` still passes).

## 16. Regression Matrix: MODE × TELEMETRY

`internal/router/p3_12_regression_matrix_test.go` — 32 combinations of
{auto, coding, reasoning, vision, fast, planning, agentic, long_horizon} ×
{none, good-aaa, poor-aaa, insufficient-aaa+good-provider} with exact
score-based expectations:

- Telemetry influences selection ONLY in planning/agentic.
- good-aaa flips planning/agentic to aaa; all other modes keep zzz (cost).
- poor-aaa → zzz everywhere (no fallback to provider data — aaa has none).
- insufficient-aaa + good-provider → provider fallback bonus ties the cost

- `TestP312RegressionMatrixTelemetryIrrelevantOutsidePlanningAgentic` locks
  the converse: identical candidates keep the deterministic tie-break in
  non-planning/agentic modes even with telemetry present.

## 19. Intentional Behaviors Retained (no fix)

- **Omitted mode ≠ explicit "auto"** in cache keys and mode-source tracking.
- **Zero success rate with samples → neutral, not penalty** (P3.11 documented
  formula; all-failures model history is not directly penalized beyond the
  health signal).
- **Cache key does not include the request alias** — aliases resolving to the
  same provider+model share cache entries (correct).
- **Planning has no context hard filter; Long Horizon has no telemetry
  preference** — deliberate mode identities (§10).
- **Unhealthy is a soft score, not a rejection** (§11).
- **Telemetry preference applies only to planning/agentic** — verified by the
  matrix (§16).
- **Context estimator stays conservative** (over-estimate by design) with
  `DefaultMaxTokens = 4096`; images +5 tokens rather than exact tokenization.

## 22. Remaining Limitations

- The context estimator remains a heuristic (chars-per-token), so exact
  tokenizer-level boundary behavior varies by provider; the boundary tests
  pin the ESTIMATOR contract, not tokenizer truth.
- The cache key includes provider name but not provider "version/endpoint"
  identity; a provider changing its base_url mid-flight keeps its entries
  (documented trade-off; TTL bounds staleness).
- `LoadCatalogCapabilities`/`SetModelCapabilities` require full struct
  population; a partial override still silently resets boolean capabilities
  (documented contract — the test harness trap was fixed; production callers
  comply).
- All-failures model telemetry stays neutral rather than penalized (§19) —
  revisit if real deployments show preference for flaky models.
- Pre-existing `gofmt` drift and unused legacy selector functions in the
  router remain out of scope for P3.12.

## 23. Recommendations / Next Stage

1. **P3.13 candidate:** make `SetModelCapabilities` merge semantics explicit
   (pointer-based optionals) so partial overrides cannot silently wipe
   capabilities.
2. Add provider-version (endpoint hash) to the cache key when a provider
   supports multiple base URLs.
3. Revisit the rate==0 model telemetry neutral case with real failure
   patterns.
4. Add a config surface for the telemetry min-sample threshold
   (`minExecutionSample = 5` is currently a constant).

## 24. Final Verdict

All six P3.11 edge-case findings are resolved: two genuine bugs fixed
(provider identity in cache key; per-signal telemetry fallback), one contract
improved (mode normalization), three verified correct and locked by tests
(planning vs long horizon, unhealthy vs circuit-open, context boundaries).
The full verification battery passes, including race detection and 10×
repetition of the router suite. No architectural redesign, no new modes, no
new telemetry dimensions, and no mode-specific scorer branches were
introduced.
