## 2. Context Estimation Approach

`EstimateRequestTokens(req)` uses a conservative **characters/4** heuristic (matching the existing `cloudflare/provider.go:estimateTokens` pattern) with structural overhead per message and per tool definition:

- Per-message overhead: 4 tokens (role prefix, delimiters)
- Text content: `ceil(len(s)/4)` tokens
- Multimodal images: 5 tokens each
- Tool definitions: 8 + function name/description tokens
- Reasoning controls: 4 tokens each for `reasoning_effort`, reasoning config fields
- `ThinkingBudget`: added linearly when set
- Output budget: `req.MaxTokens` if explicit and positive; otherwise `DefaultMaxTokens = 4096`

**Not claimed exact** — the function is named `EstimateRequestTokens` and documented as a conservative proxy.

## 3. Long Horizon Routing Semantics

**Mode activation:** `ModeLongHorizon.Active = true` with weight preferences:
- Health: 40 (strong preference)
- Capability: 45 (moderate — includes context adequacy bonus)
- Latency: 10 (secondary)
- Cost: 5 (secondary)

**Hard filter logic** (in both `selectBestProviderWithMode` and `selectFromRoutesWithMode`):
```
requiredContext = EstimateRequestTokens(req)  // only when mode == ModeLongHorizon
for each candidate:
    caps = getCapabilities(provider, model)
    if caps.MaxContext > 0 && caps.MaxContext < requiredContext:
        reject with "insufficient context (<max> < <required>)"
```

**Unknown MaxContext semantics:** When `MaxContext == 0` (unknown), the candidate is **not rejected** — it remains eligible as a fallback. This preserves backward compatibility while making known-insufficient models impossible to select.

## 4. Scoring

Among qualified candidates, the `ContextCapacity` bonus (0.10) is applied via the existing `CapabilityBonuses` mechanism in `CompositeScoreWithBonuses`. Providers with `MaxContext > 0` receive the bonus, preferring larger context headroom without changing the hard-filter contract.

## 5. Explicit Route / Fallback Behavior

- **Explicit model + mode=long_horizon**: candidates are constrained to that model; context check applies per-model.
- **Explicit route + mode=long_horizon**: only the supplied candidate set is scored; no expansion. If the single candidate fails context, returns empty selection with rejection reason.
- **Fallback routes**: primary is filtered first; if rejected, next fallback in the list is scored. Fallback selection preserves existing order semantics.

## 6. Model-Level Capability Verification

MaxContext propagation path verified:
1. `provider.ModelInfo.MaxContextLength` → catalog `Entry.MaxContextLength`
2. `catalog.Entry` → `RouterEngine.LoadCatalogCapabilities` → `SetModelCapabilities`
3. `RouterEngine.getCapabilities` hierarchy: model-specific > provider default > heuristic fallback
4. Cache key isolation: `"provider/modelID"` ensures different models on same provider keep separate context values

## 7. Trace/Observability

No trace schema changes. Context requirement metadata flows through `DecisionContext.ContextRequirement()` and is available in stage results if needed. Rejection reasons include the concrete numbers (e.g., `insufficient context (4096 < 10000)`).
