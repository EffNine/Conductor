# P3.14 Routing Decision Explainability & Policy Contract Report

## 1. Executive Summary

P3.14 delivers a canonical, immutable **DecisionTrace** contract that makes every
routing decision explainable end-to-end: what was requested, which mode resolved,
which policy capabilities were required, which candidates were considered, why
each was accepted or rejected, how each was scored (component-by-component), who
won, and which runtime snapshot justified the decision.

The work is purely **observational**: routing behavior, modes, scoring semantics,
the runtime snapshot model, and the public API are unchanged. The trace describes
the existing decision; it never recomputes it differently. Two real correctness
bugs were found and fixed (RuntimeHash single-digit encoding collapse; recorded
`CostScore` diverging from the composite score under non-default cost ceilings).
No new public endpoints, no new modes, no persistent trace storage, and no
synthetic metrics were introduced.

All verification gates pass: `go build ./...`, `go vet ./...`, `go test ./...`,
`go test -race ./...`, `go test -race -count=10 ./internal/router/...`, plus
focused P3.14 contract tests (29 tests, 2 benchmarks).

## 2. Scope

- **Deliverable:** canonical DecisionTrace contract (schema version 2) exposing
  mode resolution + policy, score components, and rejection reasons; failure
  traces for aborted decisions; corrected RuntimeHash.
- **Explicitly out of scope (per P3.14 constraints):** no new routing modes, no
  synthetic intelligence metrics, no RuntimeSnapshot redesign, no fallback
  routing, no candidate-set changes, no scoring semantic changes, no new public
  endpoints, no persistent trace storage, no load balancing. `mode` remains the
  only public routing input.

## 3. Canonical DecisionTrace Contract

`internal/router/decision_trace.go`. A trace is immutable once published
(decision ID, schema version, timestamp, and runtime hash are fixed at
construction; the builder only appends candidate scores / stage results before
publishing).

| Field | Type | Meaning |
|---|---|---|
| `DecisionID` | `DecisionID` | Unique decision identity (uuid) |
| `TraceSchemaVer` | `int64` | Contract version; **2** (bumped from 1 deliberately for the canonical contract) |
| `Timestamp` | `time.Time` | Decision time, UTC |
| `RequestedMode` | `string` | What the client asked for (`mode` field, or empty for classifier) |
| `ResolvedMode` | `Mode` | Canonical profile mode actually used (auto → `default`) |
| `ModeSource` | `string` | `explicit` \| `classifier` \| `default` |
| `ModeDescription` | `string` | Static policy description of the resolved mode |
| `ModeTraits` | `[]string` | Static policy traits of the resolved mode |
| `Intent` | `*policy.Intent` | Structured request intent from the Intent stage |
| `CapabilityRequirements` | `*policy.CapabilityRequirement` | What the request policy requires (tools, vision, context…) |
| `ContextRequirement` | `int` | Required context tokens for the decision |
| `EffectiveWeights` | `Weights` | Normalized weights actually used for scoring |
| `ModeBonuses` | `CapabilityBonuses` | Mode preference bonuses applied |
| `RuntimeHash` | `string` | SHA-256 identity of the scoring-relevant runtime snapshot |
| `CandidateScores` | `[]CandidateScore` | Authoritative candidate set with components (below) |
| `Winner` | `*ResolvedRoute` | Selected provider+model+route |
| `RejectionReasons` | `[]RejectionReason` | Hard-filter rejections with reasons |
| `StageResults` | `[]*StageResult` | Per-stage outcome (incl. failed stages) |
| `Events` | `[]EventRecord` | Full event timeline |

The builder mirrors the `DecisionContext` lifecycle: `SetModeResolution`,
`SetIntent`, `SetCapabilityRequirements`, `SetContextRequirement`,
`SetEffectiveWeights`, `SetModeBonuses`, `AddCandidateScore`, `SetWinner`,
`AddRejectionReason`, `AddEvent`, `AddStageResult`.

## 4. Candidate Score Components

`CandidateScore` (selection.go) now carries the four weighted components plus the
three additive terms, so `TotalScore` decomposes exactly (asserted to 1e-9):

```
TotalScore = wH·HealthScore + wL·LatencyScore + wC·CostScore
           + wK·CapScore + ModeBonus + ContextBonus + TelemetryPref
```

- `HealthScore`, `LatencyScore`, `CostScore`, `CapScore`: the four weighted
  factor scores (what the scorer computed).
- `ModeBonus` / `ContextBonus`: the mode preference bonus terms
  (0.05 × matching capability preference; 0.05 × context-capacity preference),
  computed by the single source of truth `capabilityBonusContributions` in
  scorer.go, shared by the scorer (adds) and the engine (records).
- `TelemetryPref`: the planning/agentic execution-telemetry preference,
  recorded before being folded into `TotalScore`.
- `TotalScore`: the exact composite the router used for ranking.

Both selection loops (`selectBestProviderWithMode`, `selectFromRoutesWithMode`)
populate components identically.

## 5. Mode Trace

The resolved mode is fully explained in the trace: `RequestedMode` (raw input),
`ResolvedMode` (canonical profile), `ModeSource` (explicit / classifier /
default), `ModeDescription` and `ModeTraits` (static policy metadata).

`ModeProfile` (mode_profile.go) gained `Description` + `Traits` for all 8 active
public modes — e.g.:

- `auto` → `default`: "baseline/general routing with global default weights",
  traits `[baseline]`
- `fast`: "latency-sensitive; health-protected; capability-neutral",
  traits `[latency_sensitive, health_protected]`
- `planning` / `agentic`: hard capability + context requirements,
  traits `[reasoning_tool_hard_requirement, context_hard_requirement, …]`
- `vision`: `[vision_hard_requirement]`, `coding`: `[tool_calling_preference,
  reasoning_preference]`, `reasoning`: `[reasoning_preference]`,
  `long_horizon`: `[reasoning_tool_hard_requirement, context_hard_requirement,
  cost_neutral]`

## 6. Capability Requirement Trace

`CapabilityRequirements *policy.CapabilityRequirement` and
`ContextRequirement int` are recorded from the capability resolution stage and
appear on every trace (including failure traces — the pipeline records them
before the requirement gate, so "why this candidate was rejected for vision /
context" is always explainable).

## 7. EffectiveWeights Trace

`EffectiveWeights` is the exact normalized weight vector the selection engine
used (`Normalize(ModeProfile.WeightPreferences → RawWeights)`). Tests verify
`trace.EffectiveWeights == profile-derived weights` for every mode, and the
component identity (section 4) verifies the weights match the score arithmetic.

## 8. RuntimeHash Contract

`RuntimeHash(snapshot)` — SHA-256 over a canonical, sorted encoding of the
scoring-relevant runtime state:

- **Included:** per-provider `State`, `LatencyMs`, `ErrorRate`, and the six
  execution telemetry counters (Successes/Failures/Timeouts/Errors/Total and
  rolling success rate) plus per-model execution counters; provider set.
- **Excluded by design:** `Timestamp`, `LastHealthCheck`, `Capacity`, `Tags`,
  `GlobalState` — they never influence scoring, so hash changes from them would
  be noise.

Contract properties (all under test):

| Property | Test |
|---|---|
| Deterministic | `TestRuntimeHashDeterministic` |
| Map-order independent | `TestRuntimeHashMapOrderIndependent` |
| Provider/model-order independent | `TestRuntimeHashModelOrderIndependent` |
| Sensitive to LatencyMs | `TestRuntimeHashLatencySensitive` |
| Sensitive to ErrorRate | `TestRuntimeHashErrorRateSensitive` |
| Sensitive to State | `TestRuntimeHashStateSensitive` |
| Sensitive to telemetry counters | `TestRuntimeHashTelemetrySensitive` |
| Sensitive to model executions | `TestRuntimeHashModelExecutionsSensitive` |
| Sensitive to provider set | `TestRuntimeHashProviderSetSensitive` |
| Insensitive to non-scoring fields | `TestRuntimeHashIgnoresNonScoringFields` |

## 9. Rejection Explainability

Every hard-rejection path produces a traceable `RejectionReason{Provider,
Reason, Required, Actual}`:

| Rejection | Reason text |
|---|---|
| Circuit breaker open | `circuit breaker open` |
| Vision gate | `vision required: request contains image content` |
| Context gate | `insufficient context (%d < %d)` |
| Agentic context gate | `agentic requires sufficient context capacity (%d < %d)` |
| Planning capability gate | `planning requires reasoning+tool_calling capabilities` |
| Agentic capability gate | `agentic requires reasoning+tool_calling capabilities` |

**UNKNOWN is never a rejection:** a candidate with unknown context
(`MaxContext=0`) is not rejected by the context gate (`TestP314UnknownContextIsNotRejection`).

When every candidate is rejected the trace still explains the decision
(`TestP314AllCandidatesRejectedTrace`), and a circuit-breaker-open candidate is
rejected with a reason instead of silently skipped (`TestP314CircuitBreakerOpenRejection`).

## 10. Failure Traces

When the pipeline aborts (e.g. inactive or invalid mode), the intent stage's
partial trace is still published and saved — a **failure trace** carrying the
mode resolution (`ResolvedMode`, `ModeSource`), stage failure, and the reason
embedded in `StageResults`. The trace is built only from data already in the
`DecisionContext` — **no second snapshot and no provider API calls**
(`TestP314NoSecondSnapshot`, `TestP314NoProviderApiCalls`). Covered:
inactive `elite` classifier result (`TestP314InactiveModeFailureTrace`) and
invalid `"banana"` mode (`TestP314InvalidModeFailureTrace`).

## 11. Policy Boundary

The full request → policy → routing chain is now visible in one trace:

```
mode input → ModeProfile (weights, bonuses, requirements, description/traits)
           → policy.Intent → policy.CapabilityRequirement → ContextRequirement
           → hard filters (capability/context/breaker/vision)
           → composite scoring (EffectiveWeights × components + bonuses + telemetry)
           → winner
```

Nothing outside this chain influences routing (verified by P3.13 matrix +
P3.14 identity tests).

## 12. Hidden Policy Audit

Audited the engine for policy decisions that were not surfaced before:

- **Hard filters in selection.go** (vision/context/reasoning/tool_calling for
  planning+agentic): mode policy, intentional (P3.13-validated). Now traceable.
- **Intensity 1.5 for agentic**, **requiredContext for long_horizon/agentic**:
  mode policy, intentional. Now traceable.
- **Name-based capability heuristics** (`strings.Contains(name, "vision"|"vl"|"reason"|"o1"|"o3"|"r1")`):
  intentional compatibility heuristics for providers without capability
  metadata (documented in capability.go).
- **`ModeProfile.Requirements` (`CapabilityProfile`)**: dead code — never read
  by routing (hard requirements live in selection.go). Left in place,
  documented (see §20).
- **No provider-identity special-casing** (no `if provider == "openai"` style
  logic) exists in the routing path.

## 13. Public API Boundary

- Public routing input remains exactly `mode` (plus the request itself). No new
  endpoints; no changes to `/v1/*` or `/api/*` responses.
- The trace is published on the existing internal event bus
  (`eventbus.DecisionTraceCreated` / `DecisionTraceCompleted`) and consumed via
  the existing `TraceStore` hook (nil-safe `saveTrace` in pipeline.go; no
  production store configured).
- `TraceSchemaVersion()` (2) is exported; schema version is distinct from
  `RuntimeHash` (which identifies the snapshot, not the trace format).

## 14. Serialization Safety

- `DecisionTrace` JSON is deterministic, nil/empty-safe, round-trips through
  `json.Marshal/Unmarshal`, handles rejection-only traces and 50-candidate
  traces (`TestP314TraceJSONSerialization`).
- **The trace never leaks request content**: no prompts, no API keys, no image
  URLs, no request bodies (`TestP314TraceNeverLeaksRequestContent`).
- `Weights` gained explicit JSON tags (`health`, `latency`, `cost`,
  `capability`) — safe because the handler serializes weights manually via
  `fiber.Map`, not `json.Marshal(Weights)`.

## 16. Observability Boundaries

- **RuntimeSnapshot** = the truth the decision was based on (single coherent
  snapshot per decision; P3.13 invariant).
- **DecisionTrace** = the explanation of the decision derived from that
  snapshot.
- **Metrics/Telemetry** (`ProviderMetrics`) = historical evidence (write-only
  for routing; never read during selection).
- The trace records what the snapshot said (`RuntimeHash`), never re-queries
  runtime state — keeping the trace faithful to the decision as made.

## 18. Bugs Found & Fixed

1. **RuntimeHash single-digit encoding collapse** (pre-existing). The original
   `int64ToString`/`float64ToString` truncated numbers to a single digit, so
   `LatencyMs=100` and `LatencyMs=1000` produced the same hash — two very
   different routing states were indistinguishable. Fixed with
   `strconv.FormatInt` / `strconv.FormatFloat('g', -1, 64)`; regression tests
   `TestRuntimeHashLatencySensitive` / `TestRuntimeHashErrorRateSensitive`.
2. **Telemetry state missing from RuntimeHash** (pre-existing). The hash ignored
   the execution telemetry counters that planning/agentic scoring actually
   reads. Fixed; regression tests
   `TestRuntimeHashTelemetrySensitive` / `TestRuntimeHashModelExecutionsSensitive`.
3. **Recorded CostScore diverged from the composite score under non-default
   `CostCeiling`** (found during P3.14). The engine's configurable
   `costCeiling` fed `cs.CostScore` while the scorer's cost factor hardcoded
   `0.001`, so with a custom ceiling the trace component did not describe the
   computed score (and the identity invariant broke). Fixed by adding
   `Scorer.SetCostCeiling` and wiring `NewRouterEngine` to sync it; the factor
   definitions in `buildFactors` and `FactorScores` were deduplicated onto the
   shared `buildFactors` path. Default behavior (ceiling 0.001) is bit-identical.
   Regression: `TestP314CustomCostCeilingConsistency`.
4. **Dead `CandidateList` field on DecisionTrace** (pre-existing) — never
   populated. Removed.
5. **Score components not recorded** (pre-existing) — `CandidateScore` lacked
   per-component contributions; the trace could not explain a total score.
   Fixed (§4).
6. **No failure traces** (pre-existing) — aborted decisions (inactive/invalid
   mode) produced no explanation. Fixed (§10).

## 19. Intentional Behaviors Preserved (verified unchanged)

- All 8 public modes route exactly as in P3.13 (regression matrix green).
- `auto` resolves to the `default` profile; classifier may still resolve to the
  inactive `elite` mode → intent-stage failure (unchanged, now traceable).
- Score ordering, candidate sets, winner selection, telemetry preference
  arithmetic, bonus magnitudes — unchanged (P3.13 score contract + P3.14
  identity tests both green).
- Cost factor default ceiling behavior is bit-identical for the default
  configuration.

## 20. Architecture Debt (documented, not refactored)

- `ModeProfile.Requirements` (`CapabilityProfile`) is dead code; the real hard
  requirements live in selection.go. Consolidating would be a routing-semantics
  change — deliberately deferred.
- `FactorScores` is unused outside scorer.go (legacy dashboard-era API). It now
  shares `buildFactors` so it cannot drift, but could be removed later.
- `HealthFactor` / `CostFactor` public factor types are unused by the routing
  path (routing uses closures in `buildFactors`).
- Trace persistence (`TraceStore`) has no production implementation; traces are
  published on the event bus and optionally stored.
- Pre-existing golangci-lint findings (errcheck, gosec, govet shadow, revive)
  remain, per repo baseline.

## 26. Recommended Next Stage

1. **Trace persistence & query** (the natural follow-up): implement `TraceStore`
   on the existing hook, expose read-only trace queries via the dashboard API
   (`GET /api/traces`, `GET /api/traces/:id`) — the contract is already stable
   enough to persist.
2. **Weight-isolation observability**: surface `EffectiveWeights` per mode in
   the dashboard to make mode-policy differences visible to operators.
3. **Consolidation of dead policy code**: fold `ModeProfile.Requirements` into
   the live selection gates or remove it (requires a routing-semantics review).
4. **Optional: hash-based cache poisoning detection** — `RuntimeHash` already
   gives a cheap way to detect snapshot invalidation between probe passes.

## 27. Final Verdict

**PASS.** P3.14 delivers the canonical routing-decision explainability contract
as a purely observational layer: every decision — success, rejection, or
aborted pipeline — is explainable from one immutable trace, with no change to
routing semantics, modes, public API, or snapshot model. Two genuine correctness
bugs (RuntimeHash encoding collapse, cost-ceiling score divergence) were found
and fixed with regression tests, and the complete verification matrix (build,
vet, full suite, race, 10× repeat, benchmarks, contract tests) is green.
